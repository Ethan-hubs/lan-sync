## 0. 本次对原始需求的完善清单

原始需求给了三个主干（**局域网同步 / 云中转 / 云端授权**）。以下是补齐后必须一并定义的部分，越靠前越是"不做就要返工"的：

| # | 补充项 | 为什么必须补 | 优先级 |
|---|---|---|---|
| 1 | **冲突与删除语义** | 同步软件最容易"丢数据"的地方，不是网络而是并发写和删除 | P0 |
| 2 | **授权失效的降级策略**（离线宽限期） | 只写"授权在云上"会做出一个"断网就罢工"的软件，工作场景不可接受 | P0 |
| 3 | **中继流量成本模型与配额** | 阿里云公网出流量 0.8 元/GB，中转跑量的成本会超过服务器本身，直接决定商业模式 | P0 |
| 4 | **防破解的关键点：把能力锁在服务端** | 客户端本地授权校验必然可被绕过；只有"中继 Token 必须由服务端签发"才是真正不可绕过的闸门 | P0 |
| 5 | **设备指纹与换机/解绑策略** | 授权按设备卖，就必须定义"什么算一台设备""换硬盘算不算" | P0 |

## 1. 产品定位（一句话）

给小型团队/个人工作室的一套**私有文件同步系统**：同一局域网内设备之间**点对点直连秒同步**；一旦不在同一网段，自动经**自有阿里云服务器加密中转**继续同步；**授权（License）与身份鉴权全部由自己掌控**，可签发、可计量、可吊销。

**与现成产品的差别（卖点）**：数据通道自建、授权不依赖第三方、局域网内网速跑满且不产生云流量费。

## 2. 背景、目标与非目标

### 2.1 背景痛点
- 现有网盘（百度/坚果云/OneDrive）在**同一办公室里也要绕公网一圈**，大文件慢、且按量计费。
- 现成同步工具（Syncthing/Resilio）要么无中心授权（管不住设备和许可），要么授权在别人手里。
- 工作文件（审计底稿、报表、扫描件）体量大、含敏感信息，**不适合第三方云**。

### 2.2 业务目标（可量化）
| 编号 | 目标 | 指标 |
|---|---|---|
| G1 | 局域网可用性 | 同网段设备发现成功率 ≥ 95%，变更到对端可见 P95 < 3s |
| G2 | 跨网可用性 | 跨网自动建立连接、无需用户操作：**能直连则优先直连，无法直连自动回落私有 relay**。**跨网直连率作为观测指标**（E4/E6 记录），**不作阶段一硬门槛**——只有公司/家里几个网络，百分比统计意义很弱 |
| G3 | 数据安全 | 同步过程中不丢文件、不静默覆盖；冲突 100% 保留双方副本 |
| G4 | 授权可控 | 新增/续期/吊销授权生效时间 ≤ 5 分钟（在线设备） |
| G5 | 成本可控 | 中继流量可计量、可配额、可告警，单租户月流量可设硬上限 |

### 2.3 非目标（明确不做，避免范围膨胀）
- 不做在线协同编辑（不是 OnlyOffice/飞书文档）
- 不做 Git 式的分支/合并语义（是文件同步，不是版本控制系统）
- v1 不做移动端、不做 Web 端上传下载门户
- 不做跨租户文件分享链接

### 2.4 实施阶段划分（2026-09-13 决策）

| 阶段 | 目标 | 包含 | **不包含** | 出口标准 |
|---|---|---|---|---|
| **阶段一：主体**（先做这个） | 「装完就能同步」——局域网直连 + 跨网自动中转 | Syncthing 原生引擎 + 局域网发现 + 跨网发现与中继回落 + 冲突与**版本恢复**（用原生能力）+ 客户端托盘 + Windows 打包 | **授权系统、账号登录、管理后台、自研 signaling、动态 relay Token、多租户数据库、商业计量计费** | 4 台设备（公司 2 + 家里 1 + 测试机）连续 2 周无数据事故 |
| **阶段二：授权** | 把「谁能用、用多少、能不能停」收回来 | License 中心（签发/激活/心跳/吊销/离线宽限）、中继动态凭证、管理后台、审计日志 | 商业化相关（计量计费、软著、隐私政策、多租户） | 后台吊销 ≤5 分钟在中继层生效 |

**阶段一的设备准入方式（关键设计，v0.7 定稿）**：

```
Windows 客户端 → 原版 Syncthing → 私有 strelaysrv -pools="" -token=<secret>
```

即 **共享 `-token`**（上游原生能力，一个配置项）——阶段一**不改 relay、不写授权、不写鉴权协议**。
⚠️ 之前写的"relay 侧静态 Device ID 白名单"**上游并不存在**（源码实测见 §12.4），已作废。
**阶段二**再单独立 ADR 决定：A. 保持原版 relay + 共享 token，放弃 relay 层单设备即时吊销；
B. fork/patch `strelaysrv` 增加"Device ID + 服务端授权"准入层（W1/W2）。**选了"≤5 分钟吊销"就等于选了 B。**

**⚠️ 阶段一有两层完全不同的「准入」，不要混为一谈（v0.9 明确）**

| 层 | 机制 | 管什么 | 谁能决定 |
|---|---|---|---|
| **① 同步成员准入** | 双方在 Syncthing 里**互加 Device ID** 并共享同一个 Folder | 谁能**看到/改文件** | 你（在客户端里加/删设备） |
| **② Relay 使用准入** | 持有私有 `strelaysrv` 的**共享 `-token`** | 谁能**占用中继带宽** | token 的持有者 |

**关键**：relay 只是传输通道，**拿到 relay token ≠ 获得文件访问权**——文件访问权只由①决定。
反过来，① 也不能保护你的账单（中继带宽是②的事）。两层各自独立。

**⚠️ 共享 `-token` 的威胁模型（v0.8 补写，必须知道）**

| 项 | 事实 |
|---|---|
| 它保护什么 | **只保护 relay 资源不被陌生人蹭用**——它不识别设备，不是身份凭证 |
| 谁能用 | **任何拿到这个字符串的 Syncthing 都能占用你的中继带宽**（含被复制到别的机器） |
| 能否按设备追责 | **不能**。泄漏后无法定位是哪台设备在用，也无法只封某一台 |
| 能否按设备限速 | 不能（只有 `-per-session-rate` / `-global-rate` 这类全局限制） |
| 缓解措施 | ① token 只发给自己人；② 定期轮换（改配置 + 重启 relay）；③ 靠打洞优先让流量尽量不过中继；④ 云监控预算告警；⑤ 阶段二 W1 升级为按设备准入 |

一句话：**`-token` 是"门禁卡"，不是"身份证"**——这正是 §12.4 里 W1（逐设备准入）存在的理由。

**关于流量：两个概念必须分开（v0.7 修正 v0.6 的自相矛盾）**

| 概念 | 阶段一 | 阶段二 |
|---|---|---|
| **技术流量监控**（防止账单失控） | ✅ 做，但**只能到全局粒度**：relay `/status` 的 `bytesProxied` + 云监控账单告警 | 保持 |
| **商业计量计费**（按设备/按人算钱） | ❌ 不做 | 需要 W2（改中继转发层）才有的**按设备归属** |

⚠️ v0.6 曾写"阶段一 `relay_usage` 按 Device ID 记录字节数"——**这与上游能力冲突，已删除**。
阶段一能拿到的只有全局数字。

### 2.5 验证实验清单（PoC 开工前必跑，半天级）

> 这是本版**新增的一等公民**：把最贵的两个未知数（中继改造量、ECS 真实边界）放在**第一天就能测**的实验里，
> 用实测数字回填 §13 / §14 / §15，而不是"先开工、边做边压测"。

| 编号 | 实验 | 做法 | 通过判据 | 失败后的备选路线 |
|---|---|---|---|---|
| **E1** | **中继准入改造可行性（非阻塞并行研究项，v0.9）** | 在本地跑 `strelaysrv`，分别试三条路：① fork 后在握手处加设备白名单 ② relay 前加自研反代做准入 ③ 自研极简 relay（只做密文转发 + 白名单 + 计量） | 能在 **≤ 2 人天**内做到"白名单外的 Device ID 被拒、白名单内的可连"；给出三条路各自的人天估算 | 若三条都超 2 人天 → 阶段一长期使用**共享 `-token`**，把"逐设备准入/计量"明确列为**独立工作项**（可能需要一台独立小机器专跑自研 relay） |
| **E2** | **ECS 真实边界** | 在 2核1.6G ECS 上压 `strelaysrv`：并发 session ↑，记内存曲线；同时实测公网带宽上限 | 得出两个数字：**不 OOM 的最大并发 session 数**、**实测出网带宽（Mbps）** | OOM 早于预期 → 升配 / 中继搬到独立轻量服务器 / 收窄为"仅按需中继（默认禁）" |
| **E3** | **Syncthing 文件语义测试集** | 双机跑：大小写碰撞（`a.txt`/`a.TXT`）、中文与 emoji 名、>260 字符路径、Office 锁文件、断网 30 分钟恢复、单文件 ≥4GB、10 万文件索引 | 全部符合 §18 阶段一验收项 | 个别用例不达标 → 调整忽略规则 / 目录映射 / 明确降级为"人工冲突处理"并写进验收标准 |
| **E4** | **真实中继出流量实测 + 打洞成功率** | ① 一次真实跨网同步，用 relay 的 `/status`（全局）与客户端侧计数交叉核对；② **同时统计打洞成功率**（G2 目标是 ≥60%），即跨网变更里有多少走了中继 | 与 §13 表的偏差 **≤ 30%**；**并给出实测的打洞成功率**（用于回填 §13 的参数化公式） | 偏差过大 → 用实测值重写 §13；成功率过低 → 中继成本按 100% 中继重算，并优先做打洞优化 |

| **E6** | **网络切换实测**（v0.9 新增，回应「5 秒切中继」） | 五种场景各 20 次，记录恢复连接时间 **P50/P95**：① 公司 Wi-Fi → 手机热点；② 有线 → Wi-Fi；③ 休眠 → 唤醒；④ 拔网线 → 恢复；⑤ 直连断开 → relay 接管 | 得出五组 P50/P95，**据此再定 SLA** | 若普遍 > 10s → 调整 `reconnectionIntervalS`（默认 **20 秒**、下限 5 秒）并重测；仍不达标则把该项从硬验收降为"最终一致" |
| **E5** | **同步时延实测**（v0.7 新增，回应「3 秒是否可达」） | 双机分别测**新增 / 修改 / 重命名 / 删除**四类操作的感知时延，各 30 次记 P50/P95；对照组：`fsWatcherDelayS` 默认 10s vs 调小（最小 0.01）| 得出四类操作的实测 P50/P95，并给出「是否保留 3 秒目标」的结论 | 若删除/重命名普遍 > 10s → 客户端在文件事件后**主动触发一次 scan**，或把该两项从"3 秒验收"里摘出，只保留为"最终一致" |

**产出物**：一份《验证报告》，用真实数字回填 §13（成本）、§14（工期）、§15（风险）三节。

| **G3** | **中继准入与计量方案定版**（**不阻塞 M1；M3 前置**） | 阶段一用共享 `-token`；W1（逐设备准入）/ W2（逐设备计量）的**人天估算**与是否 fork 的决策；确认 §9.4.1 的 adapter 抽象（`CheckJoin` / `Account`）；**产出 ADR A1** | ⏳ 并行研究（依赖 E1，不挡 M1） |
| **G4** | **验证实验 E2–E6 完成**（E1 不在此 Gate 内，见上） | 《验证报告》出炉，且 §13/§14/§15 已用实测数字回填；含《版本锁定表》（§14 M0.5） | ❌ 未做 |

### 2.7 阶段一设计原则：做减法（v0.7 新增）

> 这条路线的最大风险不是"想得不清楚"，而是**想得太多**——决定复用 Syncthing 之后，
> 原来自研路线留下的设计没有彻底删掉，结果"旧设计 / 自研设想 / 阶段二能力 / Syncthing 原生能力"混在一份文档里。
> 照这种文档开发，很容易做到 M1/M2 才发现"某些需求不是给 Syncthing 套个壳能实现的"。

**一句话原则**：

> **凡是 Syncthing 原生已经解决的问题，阶段一不在本文档里重新设计协议。
> 阶段一只自研三样东西：产品壳（托盘 UI）、适配层（Adapter）、私有部署（discovery + relay）。**

据此已经把下列条目从"自研设计"降级为"能力要求 + 采用原生实现"：

| 原文档的写法 | v0.7 改为 | 依据 |
|---|---|---|
| FR-1.2 "Rabin/gear CDC + BLAKE3" | 能力要求"块级增量"；**阶段一用 Syncthing 原生 block indexing，不改块算法**（实测 128 KiB–16 MiB 定长块 + SHA-256） | `lib/protocol`、`lib/scanner/blocks.go` |
| FR-3.5 "路径→文件ID + 块指纹 + 目录启发式判定移动" | 能力要求"移动/重命名不得丢数据"；**阶段一允许退化为删除+新增**（靠块复用减少重传），是否优化由 E3 数据决定 | 减少自研面 |
| FR-3.6 "自研反墓碑 revive 协议" | **用 Syncthing 原生版本历史 + REST 恢复**（`GET/POST /rest/folder/versions`），冲突由 UI 决策 | `lib/api/api.go` 实测存在 |
| FR-6.1 "自研 signaling" | **删除**：`stdiscosrv` + `strelaysrv` 已覆盖发现与中转，Syncthing 自己完成连接协商 | 职责重复 |
| FR-2.4 "QUIC/443 中继" | 直连 TCP/QUIC；**relay 是 TCP，可监听/映射 443** | relay 协议 |
| "TCP/443 伪装成 HTTPS 流" | **彻底废止**：443 ≠ HTTPS，只提高通过率，**不承诺 DPI 穿透** | 事实更正 |

**阶段一架构（做减法后的完整形态）**：

```
Windows 托盘 UI（自研产品壳）
      ↓
Syncthing Adapter（自研适配层，职责见 §6.1.1）
      ↓
Syncthing Headless / Windows Service（原生引擎）
      ├─ 局域网：原生 Local Discovery + TCP/QUIC 直连
      ├─ 跨网：自建 stdiscosrv（发现）
      └─ 直连失败：自建私有 strelaysrv（TCP，可映射 443，共享 -token）
阿里云阶段一只跑：stdiscosrv + strelaysrv + 基础监控
```

**阶段一明确不做**（清单化，防止回潮）：License 服务、账号 / JWT / OIDC、管理后台、自研 signaling、
动态 relay Token、多租户数据库、商业计量计费、文件夹级 ACL、选择性同步（自研 P1）、移动端 / Web 端。

## 5. 关键场景（用户故事 + 验收要点）

**U1 办公室内多机同步**
财务组 3 台电脑共享 `D:\工作底稿`（约 20GB，含 5 万个文件）。首次全量各自跑满千兆内网；之后改动一个 Excel，另两台 3 秒内可见。
*验收*：首次同步不经公网（服务端流量为 0）；未改动文件不重传。

**U2 出差/在家**
在家打开笔记本，局域网里没有同伴，客户端 5 秒内自动切到阿里云中继，继续收改动，用户无感、无需手动切换。
*验收*：切换过程不中断、不重复下载已完成部分；状态灯由"直连绿"变"中继黄"。

**U3 断网 8 小时**
地铁/断网期间本地改动照常落盘；恢复网络后自动补齐，已传块不重传，不产生冲突副本。
*验收*：断网期间的多次保存只同步最终状态，中间态不产生垃圾文件。

**U4 授权到期 / 超设备数**
客户 License 到期前 7 天开始提示；到期后进入 14 天宽限期（功能正常）；宽限期满后按策略降级（只读或停止同步），**绝不静默失效或删数据**。

**U5 离职设备吊销**
管理员后台点"吊销"，在线设备 5 分钟内停止同步并提示"授权已被管理员收回"；离线设备下次联网即失效。

**U6 完全隔离内网（无公网）**
内网无外网出口时，用**离线授权文件（.lic）**导入激活，功能完整，仅不做在线心跳（以离线文件有效期为准）。

**U7 双端同时改同一文件**
A、B 两台设备在断网期间各自改 `报表.xlsx`。恢复后不互相覆盖：Syncthing 会把较早修改时间的那个重命名为**原生冲突文件** `报表.sync-conflict-20260913-142200-B设备名.xlsx`（**磁盘上保持原生命名，不自定义**，§FR-3.2），并在托盘 UI 的「冲突」列表里显示为「报表.xlsx — 与设备 B 冲突 — 2026-09-13 14:22」，可一键打开比较。

**U8 误删恢复**
成员误删整个文件夹并已同步扩散。⚠️ **这是"版本历史"而不是"全局回收站"（v0.9 更正）**：Syncthing 的版本归档是**按设备、按 Folder 配置**的，且只在「远端变更导致本地文件被替换/删除」时才归档旧版本，**默认还是关闭的**。阶段一决定：**启用 Staggered versioning，`maxAge = 30 天`**（§FR-3.3）——因此"能恢复到哪一版"取决于该设备确实归档过哪些版本，**不能承诺从任意设备恢复任意版本**。

## 6. 功能需求

优先级：P0 = MVP 必须有；P1 = 正式版；P2 = 后续。

### 6.1 同步引擎（P0）
> **阶段一实现方式**：Syncthing（headless，关闭官方 discovery/relay）+ 自研适配层（职责见 §6.1.1）。
> **下表一律是「能力要求」，不是实现规格**——凡上游已提供的能力，阶段一直接采用原生实现（§2.7）。

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-1.1 | 文件变更监测 | **阶段一（仅 Windows）**：Syncthing 原生 watcher（Windows 文件系统通知）+ `rescanIntervalS`（默认 3600s）兜底。⚠️ 注意 `fsWatcherDelayS` 默认 **10 秒**（源码实测，可调小至 0.01）——直接影响感知时延，见 §2.5 E5。macOS FSEvents / Linux inotify：**移入 §16 backlog**，不是阶段一范围 |
| FR-1.2 | 内容分块 | **目标**：块级去重 + 断点续传。**Syncthing 实际值（源码实测）**：块切分按文件大小动态**定长**（非内容定义分块），`MinBlockSize = 128 KiB`、`MaxBlockSize = 16 MiB`，块哈希 **SHA-256**（`lib/protocol`、`lib/scanner/blocks.go`）。→ 早期写的"1–8MB CDC + BLAKE3"**与上游不符，已更正**。**阶段一不改块算法 / 不换哈希**（§2.7），仅在需要时调优块大小 |
| FR-1.3 | 增量与断点续传 | 仅传差异块；中断后从块边界续传 |
| FR-1.4 | 传输协议 | **直连**：Syncthing 原生 `tcp://`（TLS 1.3）与 `quic://`（`lib/connections/quic_*.go`、`tcp_*.go`）。**中继**：relay 协议走 **TCP**，可监听/映射到 **443** 以提高企业网通过率。⚠️ 早期"TCP/443 伪装成 HTTPS 流"的表述 **已彻底废止**：443 ≠ HTTPS，**不承诺 DPI 穿透** |
| FR-1.5 | 原子落盘 | 先写同目录 `.tmp` 再 rename；保留 mtime/权限位；禁止"边下边写目标文件" |
| FR-1.6 | 文件名兼容 | 中文/emoji/超长路径（Windows 用 `\\?\` 前缀，支持 >260 字符）；非法字符转义映射表；大小写敏感冲突检测（Windows 内部：大小写不敏感，需防"同名不同大小写"互相覆盖）；`\\?\` 前缀只绕过 MAX_PATH 与路径规范化，**不改变 NTFS 大小写规则**（R5）。**Linux→Windows 跨平台大小写碰撞用例：移入 §16 backlog**（阶段一仅 Windows，不再是 M1 硬门槛） |
| FR-1.7 | 忽略规则（**用原生 `.stignore`，v0.9 更正**） | 忽略文件是 **`.stignore`**（放在 Folder 根目录；支持 `#include`，语法是 Syncthing 自有 glob，**不是 gitignore 等价物**）；阶段一由 Adapter 通过 **REST Ignore API** 管理，UI 对用户隐藏底层文件名。
**默认只忽略明确垃圾与锁文件**：`~$*`、`.~lock.*`、`Thumbs.db`、`.DS_Store`；**`*.tmp` / `.git/` / `node_modules/` 不再默认忽略**（同步软件最怕"用户以为同步了、实际没同步"）——改为提供"开发目录忽略模板"，由用户主动开启（见 §6.8 设置项） |
| FR-1.8 | 带宽控制 | 全局/单设备限速；可选"工作时间限速、夜间全速"时段策略 |
| FR-1.9 | 打开中的文件 | 检测 Office/WPS 锁文件与独占句柄，延迟到释放后再同步，不报错打断用户 |
| FR-1.10 | 大文件与海量小文件 | 单文件 ≥ 4GB 支持；10 万文件索引重建 < 60s |


#### 6.1.1 Syncthing Adapter 职责（定死，对应 §2.6 G1）

> Adapter 是阶段一**唯一的自研技术层**。职责边界写死，避免"适配层"变成第二个引擎：

| # | 职责 | 说明 |
|---|---|---|
| 1 | **配置 Syncthing** | 读写/生成配置（设备、文件夹、忽略规则、限速、`fsWatcherDelayS`）；处理 `restart-required` |
| 2 | **添加设备 / 文件夹** | 走原生 REST，不自己实现配对协议 |
| 3 | **监听 events** | 订阅 event API：状态、连接类型（直连/中继）、进度、错误、冲突 |
| 4 | **读连接类型** | 用于托盘状态灯（绿=直连 / 黄=中继 / 红=离线） |
| 5 | **pause / resume** | 暂停恢复同步 |
| 6 | **版本恢复** | `GET /rest/folder/versions` 列出可恢复版本 → `POST /rest/folder/versions` 执行恢复；恢复前由 UI 决策"覆盖 / 另存 / 取消" |
| 7 | **进程健康检查** | 守护 Syncthing 进程（Windows Service），异常重启、版本核对 |

**不做**：不改块算法、不实现同步协议、不实现授权、不实现信令。

### 6.2 网络自适应（P0）
| 编号 | 需求 |
|---|---|
| FR-2.1 | 局域网发现：UDP 多播/mDNS（同组自动互见），也支持手动填 IP:Port（多播被禁的办公网兜底） |
| FR-2.2 | 局域网直连优先：同网段直接 TCP/QUIC，不经公网，不消耗云流量 |
| FR-2.3 | 跨网发现与打洞：跨网首次连接由**自建 `stdiscosrv`**（Syncthing 官方发现服务组件；无状态、内存开销小，与 relay 同机部署）完成地址交换，再 UDP 打洞；失败自动回落中继。**官方 global discovery 与公共 relay 全部关闭**（R11） |
| FR-2.4 | 中继回落：**relay 走 TCP**（可监听/映射 443 提升企业网通过率），服务端仅转发**密文**。设备之间的同步连接始终保持端到端加密；relay 只能看到 Device ID、IP 与字节数，看不到内容 |
| FR-2.5 | 无感切换：网络变化（Wi-Fi↔有线、VPN、多网卡、休眠唤醒）自动重连，无人工干预 |
| FR-2.6 | 中继开关：租户策略可强制"禁止中继"（纯内网合规要求）或"仅中继"（如禁止 P2P） |

### 6.3 冲突、删除与版本（P0）
| 编号 | 需求 |
|---|---|
| FR-3.1 | 冲突判定：版本向量（Version Vector）；"A 改、B 改"为并发修改 → 双保留，不覆盖 |
| FR-3.2 | 冲突呈现：**磁盘上保留 Syncthing 原生命名** `<filename>.sync-conflict-<date>-<time>-<modifiedBy>.<ext>`（**不自定义命名规则**，原生冲突文件之后会作为普通文件继续同步）；**托盘 UI 负责翻译成友好显示**（如「报表.xlsx — 与设备 B 冲突 — 2026-09-13 14:22」），Adapter 只做展示层转换 |
| FR-3.3 | 删除与版本（**按 Syncthing 原生 versioning，v0.9 重写**） | ① 阶段一**启用 Staggered versioning，`maxAge = 30 天`**，归档目录 `.stversions`（Folder 内，默认路径）；② 归档只发生在「**远端变更替换/删除本地文件**」时，本机自己删的文件**不会**被本机归档；③ 版本是**按设备、按 Folder 配置**的，因此恢复能力取决于该设备有无该版本；④ 不承诺"全局回收站"，也不承诺"从任意设备恢复任意版本" |
| FR-3.4 | 版本历史：**阶段一直接用 Syncthing 原生 versioning**（按设备、按文件夹配置）+ REST `GET /rest/folder/versions` 查看、`POST /rest/folder/versions` 恢复（`lib/api/api.go` 实测存在）。⚠️ 版本归档发生在"远端变更替换/删除本地文件"时，因此**可恢复性限于本设备确实存有该历史版本的场景**——"管理员可在任意设备恢复"这个承诺**已收窄** |
| FR-3.5 | **能力要求**：移动/重命名**不得导致数据丢失**。阶段一允许**退化为"删除 + 新增"**，由 Syncthing 原生块复用把重传量压到最低；是否进一步做移动识别优化，**由 E3 实测数据决定**，不在阶段一预设实现 |
| FR-3.6 | 恢复语义（**阶段一用原生，不自研协议**） | 恢复路径＝托盘 UI → `GET /rest/folder/versions` 列出**本设备**可恢复版本 → 用户选择 → `POST /rest/folder/versions`（**恢复回原相对路径，原生 API 没有"另存"参数**）→ 恢复出的文件按正常本地变更重新同步。
**阶段一只提供「恢复 / 取消」两个动作**；"另存为新文件名"需要 Adapter 额外实现「读历史版本 → 写新文件」，**不是原生能力，阶段一不做**（v0.9 收敛）。~~反墓碑 / 递归 revive / 块引用过期~~ **已作废**（§2.7） |

### 6.4 授权中心 License（**阶段二**；阶段一不实现）
> 授权「售卖的是许可」，鉴权「识别的是人和设备」——两者表结构、生命周期、失败策略都不同，必须分开。
> **阶段一不实现本节任何条目**：设备准入用 §2.4 的**共享 `-token`**（上游原生），本节内容在阶段二落地，顺延不影响阶段一交付。

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-4.1 | 授权维度（**简化版**，适用自用+小团队） | License Key + 设备数上限 + 有效期 + 可选功能位；**不做**计量计费、按席位计费、试用期、软著（归入 P2，将来要卖再补） |
| FR-4.2 | 在线激活 | `License Key + 设备指纹` → 服务端校验（未超限/未吊销/未过期）→ 下发**Ed25519 签名**的 License Blob |
| FR-4.3 | 离线激活 | 导出 `.lic` 文件用于隔离内网；有效期自签发起算 |
| FR-4.4 | 本地验签 | 客户端内置公钥，离线可验 Blob 真伪与有效期（无需联网也能用） |
| FR-4.5 | 设备指纹 | 取 4–6 项稳定标识（MachineGuid、主板 UUID、系统盘序列号、CPU 型号、MAC 集合）加权哈希；**允许 1 项变更**（换硬盘/网卡不失效），2 项以上需重新激活 |
| FR-4.6 | 心跳续期 | 默认每 24h（可配 1h–7d）上报；服务端可即时下发吊销/降级/续期 |
| FR-4.7 | 离线宽限期 | 默认 14 天（可配 0–90 天）；宽限期内功能正常，**中继可用性靠服务端预签发的凭证维持**（见 FR-4.12，凭证在心跳时批量下发）；超期策略可选：① 只读 ② 停止同步 ③ 降级为纯局域网（R2′） |
| FR-4.8 | 防时间回拨 | 单调时钟 + 上次心跳时间双记录 + 服务端 nonce 签名，回拨超阈值即启动宽限倒计时 |
| FR-4.9 | 解绑换机 | 用户自助解绑（每月 1 次）+ 冷却期 7 天；管理员后台不受限 |
| ~~FR-4.10~~ | ~~试用~~ | **已砍（R9）**：自用+小团队场景下发行方＝使用者，试用机制（防重复试用、时间回拨检测）纯属复杂度 |
| FR-4.11 | 提示分级 | 授权类异常（到期/超限/吊销）**必须弹窗明示**，绝不静默降级 |
| FR-4.12 | **中继凭证（运营闸门）** | 全部由**服务端签发**：单张 ≤ **1 小时**、心跳时**批量预签发 24 张**（客户端缓存消费，授权服务短时不可达时仍可续用，静默窗口上限见 §9.2）；凭证 claims **绑定 Syncthing Device ID（= 设备证书指纹）**，relay 侧核对握手证书指纹 → **凭证被提取也无法在其它设备使用**；relay 侧维护**已吊销 Device ID 黑名单**（授权服务推送）→ 吊销在中继层即时生效。**明确不做**客户端本地派生凭证（签发权必须留在服务端）（R2′）。**本节属阶段二**；阶段一先用**上游原生共享 `-token`**（零代码），逐设备准入/计量属**改造工作项 W2**（§12.4） |

**Windows 落地优先级（R10，必须做的不多，但一件都不能少）**：
1. **代码签名证书**（P0）——没有它分发不下去；

3. **签名安装包（MSI / Inno Setup）**（P0）——企业 EDR 会直接阻断无签名安装包；
4. 企业 EDR 白名单申报（P1）——**不提前做**，只有目标机确实装了企业级 EDR 才需要。

## 9. 关键流程

### 9.0 阶段一：设备入网与连接（无授权，先保证主体）

1. 各端首次运行 → 生成 Syncthing Device ID（= 设备证书指纹）→ 客户端显示短码 / 二维码
2. 任一端的「添加设备」里输入对方短码（或扫码）→ 双方互相接受 → 建立互信（互加 Device ID）
3. 跨网互通：**不存在"登记进 relay 白名单"这一步**——relay 侧只配一个共享 `-token`（全体客户端共用同一个字符串），所有客户端带上它即可连接（§12.4；逐设备 ACL 是 W1 工作项，属阶段二）
4. 之后全自动：同网段走局域网直连（§9.3），不同网段自动走中继（§9.4）

> 阶段一没有「激活」这一步，也没有 License 校验；能让设备加入的只有「**手工互加 Device ID**」＋「持有 relay 的共享 `-token`」两件事。
> 这在自己人小范围共用的前提下可接受（D1 决策）；放开使用范围或对外时，必须先上阶段二的授权体系。

### 9.1 激活（**阶段二**）
1. 客户端首次启动 → 生成本机指纹 → 弹激活窗（输入 License Key 或导入 .lic）
2. 联网：`POST /v1/license/activate` → 服务端校验租户/席位/设备数/状态 → 返回签名 Blob（含 not_after、grace_days、features、issuer、nonce）
3. 客户端内置公钥验签 → 存本地 → 进入正常同步
4. 离线：管理员在后台导出 `.lic`（内含该设备指纹）→ 手工导入

### 9.2 心跳与吊销
每 24h 上报 `POST /v1/license/heartbeat`，携带 Blob 版本 + 上次服务端时间戳。防雪崩与失败处理：
- 正常 → 返回 `200 + 新 Blob（如续期）` **+ 一批中继凭证**（见 FR-4.12），客户端刷新本地有效期
- 已吊销 → `403 revoked` → 立即停同步 + **弹窗明示**（不静默）
- 不可达 → 进入宽限倒计时（本地记录连续失败次数与时长）；重试采用**指数退避 + 恢复期随机错峰窗口**（替代原"±10% 抖动"，R6′）
- 服务端连续 5xx → 客户端**静默重试**，但静默窗口 **≤ min(心跳间隔 × 3, 宽限期剩余时长 × 20%)**；
  超限必须弹窗告知"授权服务不可达，已进入宽限期"——与 FR-4.11"绝不静默降级"对齐（R6′）

### 9.3 连接建立（**全程 Syncthing 原生，v0.9 整节重写**）

> 阶段一**不设计任何自研网络协议**：没有自研 mDNS 服务、没有 workspace 广播、没有自研 signaling、没有自研打洞。
> 下面写的是"原生流程长什么样"，供理解，不是要实现的东西。

**局域网内（同网段）**

```
Syncthing → 原生 Local Discovery（UDP；IPv4 用广播 255.255.255.255、IPv6 用多播 ff12::8384，端口 21027）
          → 获知对端 Device ID + 地址 → 直接 TCP/QUIC 连接
```
⚠️ 更正：早期文档写的「多播组 239.x.x.x:50000 / mDNS `_lansync._udp` / workspace_id 广播」**全部作废**——
那是自研方案的残留，与原生 Local Discovery 不是一回事。

**跨网（不同网段）**

```
Syncthing → 查询自建 stdiscosrv（替代官方 global discovery）
          → 尝试原生直连（含 UPnP / NAT-PMP 端口映射与 hole punching）
          → 仍无法直连 → 自动回落到自建私有 strelaysrv
```
NAT 穿透能力**由 Syncthing 原生提供**，阶段一不自己实现打洞。

**为什么这样最简单**：以上全部是 Syncthing 的既有行为，阶段一要做的事情只有三件——
① 关掉官方 discovery/relay；② 把 `stdiscosrv` / `strelaysrv` 地址写进客户端配置；③ 给 relay 配共享 `-token`（§2.4）。

### 9.4 中继回落
1. 中继凭证由授权服务在**心跳时批量预签发**（单张 ≤ 1 小时，一批 24 张），客户端缓存消费；
   claims 绑定 **Syncthing Device ID（= 设备证书指纹）**
2. 携带凭证连 relay 节点 → relay 核对**握手 TLS 证书指纹与凭证声明一致**（凭证被提取也无法在其它设备使用）→
   只做密文转发与计量 → 不解析内容
3. 授权服务向 relay **推送已吊销 Device ID 黑名单** → **吊销在中继层即时生效**（满足 G4 ≤5 分钟），
   不必等凭证自然过期
4. 授权服务短时不可达 → 消费缓存凭证继续中转；缓存耗尽且已达 FR-4.7 宽限期上限 → 按策略降级

**阶段一的差异（v0.6 更正）**：第 1–3 步换成「客户端携带**共享 `-token`** 即可连接」——这是上游原生能力、零代码。⚠️ **原先写的"relay 侧静态 Device ID 白名单"与"按设备记录字节数"在上游并不存在**（源码实测：无白名单/黑名单，`bytesProxied` 是全局计数器），二者属于**改造工作项**：**W1＝逐设备准入白名单、W2＝逐设备流量计量**（§12.4）。阶段一先接受「共享 token + 全局流量监控」的粗粒度形态。

### 9.4.1 准入适配层（阶段一 / 阶段二共用同一抽象）

> 第二轮评审建议：**把"准入"做成可插拔接口**——这样 D7 的"授权后置"才是真的后置，
> 而不是将来把准入逻辑重写一遍。

| 阶段 | 实现 | 内容 | 代码量 |
|---|---|---|---|
| 阶段一 | `AllowlistAdapter` | 上游原生：**共享 `-token`**（一个配置项） | ~0（配置） |
| 阶段一+ | `AllowlistAdapter`（逐设备版） | W1 改造后的白名单 + 黑名单校验 | W1 工作量 |
| 阶段二 | `CredentialAdapter` | 授权服务签发凭证（绑定 Device ID）+ relay 侧校验 + 吊销黑名单推送 | R2′ 工作量 |

**两侧共同遵守的抽象**（中继与客户端都不依赖具体实现）：

```
CheckJoin(deviceID, credential) -> allow | deny(reason)
Account(deviceID, bytes_in, bytes_out)      # 计量钩子（阶段一可为空实现）
```

凡"转发逻辑"以外的判断一律走这两个钩子 ⇒ 换准入方式时**只替换 adapter，不动转发层**。

### 9.5 冲突处理
- 收到远端变更时，本地文件同时被改（版本向量中两分支互不包含）→ 不覆盖，写冲突副本（`原名 (冲突·设备名·时间戳).扩展名`）
- 单方变更 → 直接应用；删除 vs 修改 → 保留修改版并提示

## 12. 技术路线（**已选 B：复用 Syncthing + 自建运营层**，2026-09-13 定）

### 12.1 A（全自研）与 B（复用 Syncthing）的实际差别

两者差的不是"先进程度"，而是**你的时间花在哪儿、什么时候能用上、授权能做到多硬**。

| 维度 | A 全自研 | B 复用 Syncthing + 自建运营层 |
|---|---|---|
| 出可用成品的时间（经验估计） | 6–12 个月（单人+AI 辅助） | **阶段一可用版 2–4 周**（局域网主体 + 跨网中继用共享 token）——**不含**中继逐设备改造（W1/W2）、代码签名证书采购周期（约 1–2 周流程）、CI 流水线 |
| 主要工作量 | 70% 花在同步引擎的坑（增量分块、冲突判定、跨平台文件监听、原子落盘、断电自愈、海量小文件、中文/emoji/超长路径） | 70% 花在你真正在意的地方（授权中心、阿里云中继、管理后台、客户端体验） |
| 数据保密性 | 自己实现，安全性取决于你写对没有 | 设备间本来就 TLS + 设备证书（Device ID = 证书指纹）；**中继服务器只转发密文**，官方明确 relay 无法查看内容 → 天然满足你的 E2EE 选择 |
| 云端要存密文副本时 | 需自己设计端到端加密格式 | 有现成的「Untrusted（Encrypted）Device」：文件数据、**文件名/目录结构/时间戳/哈希全部加密**（XChaCha20-Poly1305 + AES-SIV，密钥由密码 + folder ID 经 scrypt 派生）——官方标注仍是 beta |
| 自建中转 | 自己写中继协议 | 官方组件 `strelaysrv`（默认 22067 / 状态 22070，有 Dockerfile）**可跑在阿里云**，客户端可配置只使用指定 relay；**但它只提供"转发 + 全局限速 + 全局共享 token"**——按设备的准入、计量、黑名单**上游都没有，需要改造**（§12.4，工作量列 W1/W2） |
| 客户端外观 | 全部自研 | Syncthing 可 headless 运行（`--no-browser` + 本地 GUI 地址关闭），通过 REST API 全权控制；界面 100% 自研，用户看不到上游痕迹 |
| 授权强度 | 可写进协议层（无有效 License 则握手失败），技术层面最硬 | 授权在**外层**实现（启动前校验、自有中继凭证、成员准入、配置下发）：合规与管理层面可控，但**挡不住用户绕过客户端直接跑原版 Syncthing**（诚实说明：对"自用+小团队、自己就是发行方"完全够用；对外卖则强度不足） |
| 许可与合规 | 无第三方许可约束 | MPL-2.0：闭源集成 OK，只有改动其源文件才须公开该文件；不用它的官方发现/中继服务器，改用自建的即可 |
| 长期自主性 | 100% 自己的东西，可任意魔改 | 受上游迭代节奏约束（但协议稳定、社区活跃十余年） |

### 12.2 结论与建议

- 你的三个回答已经把范围收得很清了：**自用+小团队（授权要简单）** + **要 E2EE** —— 这两条恰好都是 B 路线的舒适区：E2EE 是 Syncthing 的默认形态，中继只转发密文，无需你额外设计加密层。
- 建议 **B 起步，但把引擎关进一层"适配层"**（自己的接口 + 配置文件生成 + 进程守护），将来真要做自己的引擎，替换的是这一层，不动上层业务。
- 唯一需要接受的结构性妥协：**B 的授权是"管理型授权"而不是"密码学授权"**。对这个使用范围，够；若哪天要对外销售，需要重估（届时 A 路线或上游商业授权）。

### 12.4 上游 `strelaysrv` 能力实测核验（2026-09-13，源码级）

> 结论一句话：**"官方组件直接跑在阿里云"只覆盖转发本身。凡是"按设备"的能力——准入、计量、黑名单——上游都没有，
> 必须改造。** 这不是设计错误，是**记账错误**：之前把"改中继"记成了"零代码"。

| 能力 | 上游是否有 | 实测证据 | 我们的处置 |
|---|---|---|---|
| 全局共享 token 准入 | ✅ **有** | `main.go:96` 定义 `-token`；`listener.go:127` 比对后返回 `ResponseWrongToken` | **阶段一直接用**（零代码） |
| 全局 / 单会话限速 | ✅ **有** | `-global-rate`、`-per-session-rate`（`main.go:92-93`） | 直接用 |
| 连接数保护 | ✅ 有（非配额） | 基于 rlimit 的 `descriptorLimit`（`main.go:148、320-324`） | 作为兜底，不当配额 |
| **按设备白名单 / 黑名单** | ❌ **无** | 全仓库 `whitelist/blacklist/allowlist/denylist` **零命中**；Device ID 只用于证书身份（`listener.go:98`）、outbox 路由（`listener.go:21/166`）、会话两端标识（`session.go:111-114`）、资源回收（`session.go:81/94`）——**都是路由与身份，不是准入** | **W1 工作项**：fork/patch 中继，或反代自研准入，或自研极简 relay（三选一，见 §2.5 E1） |
| **按设备流量计量** | ❌ **无** | `bytesProxied` 是**包级全局** `atomic.Int64`（`session.go:27`），session 结构体只有 id 无计数器；`/status` 只输出 `numActiveSessions / numConnections / numProxies / bytesProxied`（`status.go`），**零设备维度** | **W2 工作项**：改中继转发层，或在客户端侧近似自报（精度差） |
| 协议里带 Device ID？ | ✅ 带，但**不用于准入** | `session.go:111-114` 的 `serverid/clientid` 是会话标识与路由 | 纠正 §19.1 早期的错误表述："relay 协议本身就基于 Device ID 鉴权"**只对了一半** |

**两条工作项的量级（保守估计，需 E1 实验确认）**

| 编号 | 工作项 | 内容 | 估时 | 维护代价 |
|---|---|---|---|---|
| W1 | 逐设备准入白名单 + 吊销黑名单 | 在 relay 握手阶段校验 Device ID 是否在白名单/黑名单内（含授权服务推送黑名单的通道） | 2–5 人天（fork 路线） | **需跟上游同步**（每次上游发布要 rebase） |
| W2 | 逐设备流量计量 | 在转发层按 Device ID 累加字节数并暴露接口，供 `relay_usage` 落库 | 2–4 人天 | 同上 |

> 因为 W1/W2 都要动中继代码，**"fork 中继"这件事本身就是一个长期承诺**，必须在 §2.6 G3 里显式决策
> （选项：fork 后跟上游 / 反代自研准入 / 自研极简 relay / 接受粗粒度不做）。

## 13. 中继成本测算（决定模式能否成立）

阿里云中国大陆地域：**公网出流量 0.8 元/GB，入网流量免费**（按使用流量计费，价格以控制台实时为准）。

| 场景 | 每天改动量 | 接收端设备数 | 每月中继出流量 | 流量费 |
|---|---|---|---|---|
| 自用小团队（本项目的实际场景） | 2GB | 3 | ~180GB | **~144 元/月** |
| 同上，但改上来的都是大文件 | 5GB | 3 | ~450GB | ~360 元/月 |
| 有人误把 500GB 素材放同步目录 | 500GB（一次性） | 4 | 2000GB | **~1600 元（单次）** |

**⚠️ 多端复制倍数（v0.6 新增，之前漏算）**：中继只看到密文，**无法做跨设备去重**，所以
**一次改动产生的中继流量 ≈ 改动量 × 接收端数量**（未被局域网直连截住的那部分）。
上表第 1 行就是按 3 个接收端算的：2GB × 3 × 30 天 ≈ 180GB。设备越多，倍数越大。

**⚠️ 但上表是"跨网流量 100% 走中继"的上界（v0.8 补充参数化公式）**

G2 自己定的目标是**打洞成功率 ≥ 60%**，所以真实中继流量应当按成功率打折：

```
中继出流量 ≈ 跨网改动量 × (1 − 打洞成功率) × 接收端数量
按 60% 成功率、2GB/天、3 个接收端：2 × 0.4 × 3 × 30 ≈ 72GB/月 ≈ 58 元/月
                         按 0% 成功率（全中继）：180GB/月 ≈ 144 元/月
```

**也就是"上表是悲观上界（钱往多了算）"**。所以 E4 必须同时测**打洞成功率**，否则成本会按最坏情况估计。

结论：
1. **局域网优先不只是体验，是毛利**——办公室内跑中继的每一 GB 都是净亏。
2. 必须有**控制手段**，否则一次误操作就是一张账单。**但要按阶段区分（v0.8 修正与 §2.4 的矛盾）**：
   - **阶段一**：全局配额（`-global-rate` `-per-session-rate`）＋ **云监控预算告警**（阿里云侧设阈值）＋ **打洞优先**——设备级月度硬顶**做不到**（上游无按设备计量，§12.4）。
   - **阶段二（W2 之后）**：按设备/租户的月度硬顶与超额断流。
3. 降本手段：打洞优先（失败才中继）、块级去重（**仅限单次传输内的块级复用**——E2EE 下中继无法跨设备去重）、月度硬配额、超大文件引导走 OSS/对象存储；**控制接收端数量本身也是一种降本**（倍数效应）。
4. 现有阿里云 ECS（<YOUR_ECS_IP>，2核1.6G/40G）**算力够跑授权+信令+小规模中继，但带宽与内存必须实测**（R8）——**上线前必须压测两项，且禁止用估算数字代替实测**：
   ① **ECS 公网带宽上限**（决定"20GB 跨网首次同步"的真实耗时，以及是否要升配或改按流量计费）；
   ② **`strelaysrv` 并发 session 数与常驻内存的关系曲线**，并确认长时大文件传输下内存**不单调增长**（流式转发理论上与传输量无关，需实测确认无缓冲累积）。
   压测结论出来之前，中继一律按"配额 + 限速"上线。

## 18. 验收标准（可测）

> **阶段一必过**：第 1、2、3、4、8、10、11 条（第 1 条按 E5 实测口径）；第 12 条在阶段一改为「未持正确 relay `-token` 的客户端连不上私有 relay（relay 使用准入）；而未被互加 Device ID 的设备即使拿到 token 也看不到任何文件（同步成员准入）——两层分开验」。
> **阶段二验收**：第 5、6、7、9、13 条（授权宽限、后台吊销、离线 .lic、时间回拨、中继层即时断流）。

1. 同网段两台设备：新增/修改/删除/重命名 4 类操作，**记录各自的 P50/P95 实测值**（E5），并按下表判定（**局域网同步期间"经 Relay 的文件负载公网流量 = 0"**——注意不是"ECS 总公网流量 = 0"：客户端仍会向 `stdiscosrv` 宣布/查询地址，这部分 discovery 元数据流量不计入本条）（**v0.8 给出阈值，否则本条没有判定力**）：
| 实测 P95（新增/修改） | 判定 |
|---|---|
| **≤ 3s** | ✅ 达标 |
| **3–10s** | ⚠️ 可接受，但须在报告里写明原因（如 `fsWatcherDelayS` 默认 10s）与是否调优 |
| **> 10s** | ❌ 不达标，必须给出缓解措施（调小 `fsWatcherDelayS` / 客户端事件后主动触发 scan / 明确该项为"最终一致"并写入验收标准） |
   删除/重命名单列，允许更宽松，但**必须记录实测值**。服务端公网流量为 0。
2. 20GB / 5 万文件首次同步：不丢文件、不产生重复文件、支持断点续传。
3. 拔网线 5 分钟后恢复：自动补齐，无重复传输，无异常冲突副本。
4. 跨网（家中 → 公司）：无需任何手动配置即自动建立连接（能直连则直连，否则回落 relay）。**具体秒数按 E6 实测后确定的 SLA 判定**——此前写的"5 秒"未经验证，已撤为待定（v0.9）。
5. 授权到期：进入宽限期提示明确，宽限期满按配置降级，**任何情况下不删用户数据**。
6. 后台吊销设备：5 分钟内该设备停止同步且提示原因。
7. 隔离内网：导入 `.lic` 后可完整同步，无公网依赖。
8. 双端并发修改同一文件：产生冲突副本，原文件不丢，两个版本均可打开。
9. 系统时间回拨 24 小时：授权状态不被延长，进入宽限倒计时。
10. 卸载客户端：不残留同步文件、不留后台上传进程。
11. 版本恢复（按 Syncthing 原生语义，v0.9 重写）：在**确有该版本归档**的设备上，用 UI 选择版本并恢复成功；恢复后该文件按正常变更重新同步到其它设备；**不承诺"任一设备恢复任意版本"**，也不承诺"另存为新文件名"。
12. 把中继凭证复制到另一台设备使用：relay 握手被拒（凭证绑定 Device ID）。
13. 后台吊销设备后：该设备在**中继层 ≤5 分钟**断流（不只是本地停止同步）。

### 1. 一句话结论

**"局域网直连优先 + 跨网自有云中继 + 自带授权鉴权"三合一的开源项目，GitHub 上没有。** 你的组合本身就是空白位；但三块拼图各自都有成熟零件，其中 **Syncthing 一家独大（88,505★，MPL-2.0），而且"自建中继服务器"的源码就在它主仓库里**（`cmd/strelaysrv`、`cmd/stdiscosrv`，实测确认），与"阿里云中转"需求精确对应。

### 4. 许可证红线（务必遵守）

**可安全闭源集成**：MIT、Apache-2.0、BSD 系列、MPL-2.0（MPL 仅"被修改的文件"需开源）。
**慎用（传染性）**：AGPL-3.0（Nextcloud、Alist、Cells、Sync-in、Seafile CE）、GPL-3.0（Cloudreve、unison、warpinator、linker）。
**非开源陷阱**：
- **keygen-api = Fair Core License**：内部使用可，商业托管/转售需付费。
- **kodbox 仓库无 LICENSE 文件**：不能默认可用。
- **verysync 闭源**，GitHub 无官方仓库。

**GitHub 元数据显示"未识别"≠ 可商用**：coturn、seafile、mutagen、licensepp、ZeroTier、KDE Connect 等为"未识别/Other"，落地前必须打开其 LICENSE 文件逐字确认。

#### 附 B · GLM-4.5-Air 同题独立意见（交叉验证用）

## 评审意见

### A级（一定会返工或出事）

1. **结论**：冲突处理机制未考虑系统时间不同步情况，可能导致版本向量判断错误和数据不一致。**理由**：分布式系统中时间不同步会导致版本向量无法正确反映操作先后顺序。**依据**（§6.3、§9.5）。

2. **结论**：删除语义的墓碑机制缺少墓碑同步和清理的详细说明，可能导致删除操作在不同设备间不一致。**理由**：墓碑本身也需要被同步和及时清理，否则会积累大量无效元数据。**依据**（§6.3）。

3. **结论**：设备指纹变更判定标准模糊，可能导致用户频繁需要重新激活或系统误判。**理由**：没有明确定义如何量化"1项变更"与"2项变更"的界限，以及如何处理中间状态。**依据**（§4.5）。

4. **结论**：中继Token设计过于复杂，对于"自用+小团队"场景增加不必要运维负担。**理由**：短时效Token续签机制在网络不稳定环境下可能导致频繁授权失败。**依据**（§FR-4.12、§9.4）。

5. **结论**：成本测算不全面，忽略了阿里云ECS实例本身的成本和其他潜在费用。**理由**：仅考虑流量费用而忽略计算资源成本，可能导致实际运营成本远超预期。**依据**（§13）。

6. **结论**：文件系统兼容性考虑不足，如USN Journal仅适用于NTFS。**理由**：未明确说明对非NTFS文件系统的支持策略，可能导致功能降级或数据丢失。**依据**（§6.1）。

### B级（建议修改）

1. **结论**：产品定位中"数据通道自建"与实际使用阿里云ECS存在表述不一致。**理由**：使用第三方云服务不能称为"自建"，这会影响用户对数据控制权的理解。**依据**（§1、§7）。

2. **结论**：用户角色设计（超级管理员、租户管理员）与"自用+小团队"的简化授权需求存在冗余。**理由**：复杂的角色划分会增加小团队的使用门槛和管理成本。**依据**（§3、§4.1）。

3. **结论**：非功能需求中的内存占用要求（<150MB）对于2核1.6G的ECS来说过于宽松。**理由**：此要求可能导致系统在高负载下性能不足，影响用户体验。**依据**（§11）。

4. **结论**：没有说明当网络不稳定时Token续签失败的处理策略。**理由**：续签失败会导致同步中断，但文档未提供降级或容错方案。**依据**（§9.4）。

# 附录 D：同步数据表现（流量 / 去重 / 最坏账单）

> 这是这个项目**唯一会让人真掏钱**的地方（v0.6 新增，回应第二轮评审第 14 条）。

## D.1 数据是怎么走的

| 路径 | 数据形态 | 谁看得到 |
|---|---|---|
| 局域网直连（同网段） | 设备间 TLS 密文 | 只有两台设备；**不产生云流量、不产生费用** |
| 图打洞成功（跨网 P2P） | 设备间 TLS 密文 | 只有两台设备；信令服务只知道"谁连过谁" |
| 中继回落（打洞失败） | 设备间 TLS 密文，经 relay 转发 | relay 看到密文 + 设备 ID + 连接时长 + 字节数；**看不到内容** |

## D.2 多端复制倍数（成本的核心变量）

中继只搬密文 ⇒ **无法跨设备去重、无法合并多播**：

```
一次改动 1GB，3 台接收端 → 中继出流量 ≈ 3GB（未被局域网直连截住的部分）
10 台接收端            → 中继出流量 ≈ 10GB
```

| 接收端数 | 倍数 | 每天改 2GB 的月度中继流量 | 月费（0.8 元/GB） |
|---|---|---|---|
| 1 | ×1 | 60GB | ~48 元 |
| 3 | ×3 | 180GB | ~144 元 |
| 5 | ×5 | 300GB | ~240 元 |
| 10 | ×10 | 600GB | ~480 元 |

**结论**：控制成本的三根杠杆，按性价比排序 = ① 让更多传输走局域网直连（免费）② 打洞成功率（免费）③ 减少接收端数量（不改代码）。

## D.3 E2EE 下什么能去重、什么不能

| 场景 | 能否去重 | 说明 |
|---|---|---|
| 同一文件、同一次传输内的重复块 | ✅ 能 | 块级复用（Syncthing 原生能力） |
| 同一文件、跨设备重传 | ✅ 能 | 发送端只发对端缺的块（协议层） |
| 两个不同文件含相同内容 | ✅ 部分能 | 块哈希相同则复用（同一次会话内） |
| 云端跨租户/跨文件全局去重 | ❌ **不能** | 服务端只见密文，这是 E2EE 的固有代价 |
| 多接收端的一次改动 | ❌ **不能** | 每个接收端各收一份 ⇒ 倍数效应（D.2） |

## D.4 最坏情况账单（用来定配额上限）

| 最坏情形 | 中继流量 | 费用 |
|---|---|---|
| 误把 500GB 素材放进同步目录，4 台接收端 | 2000GB | **~1600 元（单次）** |
| 设备被搬走/被盗，一直在同步，配额没设 | 无限（按 1GB/天 计约 30GB/月） | ~24 元/月起，且**持续** |
| 打洞全失败 + 每天改 5GB + 3 端 | 450GB/月 | ~360 元/月 |

**因此必须有的三道闸**（已写进 §FR-6.6 / §13）：设备级并发上限、月度总量硬顶、80%/100% 双档告警。
**阶段一**（无逐设备计量）至少要有：relay 全局流量监控 + 云监控账单告警（阿里云侧设置预算提醒）。
