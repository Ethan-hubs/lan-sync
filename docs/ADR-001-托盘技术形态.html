1. 选型：WPF（不是 WinForms）

决定：托盘壳用 WPF，目标框架 net10.0-windows10.0.17763.0（平台版本必须编码进 TFM，见 §1.1），最低 OS 10.0.17763.0（Win10 1809）。

依据 - PRD 附录 F 与 FR-6.8 指定的参考实现是 GermanCoding/SyncTrayzor（续维护版，MIT，C#），其本身就是 WPF。 - 托盘要呈现的都不是"表单"：状态灯 + 同步进度/速率 + 冲突列表（需翻译后的友好文案）+ 恢复面板（列版本、选择、恢复）。这类列表/模板/数据绑定用 WPF 明显更省事，WinForms 会写成大量手工布局代码。

1.1 TFM 必须带平台版本（ADR 修订，2026-09-15 实测）

net10.0-windows（不带平台版本）配 SupportedOSPlatformVersion=10.0.17763.0 直接编译失败： MSBuild 的 GetTargetPlatformVersion 对无版本的 windows TFM 一律取 7.0，于是报 NETSDK1135: SupportedOSPlatformVersion 10.0.17763.0 cannot be higher than TargetPlatformVersion 7.0。 在 csproj 里显式写 <TargetPlatformVersion>10.0.17763.0</TargetPlatformVersion> 无效（会被推理目标覆盖回 7.0）。

主线用 SDK 10.0.401 复核三种写法（对照实验）：

csproj 写法 实际 TargetPlatformVersion 结果
net10.0-windows + SupportedOSPlatformVersion 7.0 ❌ NETSDK1135
net10.0-windows + 显式 TargetPlatformVersion 7.0 ❌ NETSDK1135（显式值被无视）
net10.0-windows10.0.17763.0 10.0.17763.0 ✅ 构建通过

结论：托盘工程 TFM 一律写 net10.0-windows10.0.17763.0。这不是抬门槛——17763 就是 Win10 1809，与 SupportedOSPlatformVersion 同值；仍然禁止 10.0.22000.0 及更高（那才是 Win11）。

2. 托盘图标实现：同工程启用 WinForms 的 NotifyIcon，阶段一不引第三方包

决定：LanSync.Tray.csproj 同时设 UseWPF=true 与 UseWindowsForms=true，托盘图标用 System.Windows.Forms.NotifyIcon + ContextMenuStrip。

依据：NotifyIcon 由 Windows Desktop SDK 内置，零 NuGet 依赖——实现机网络受限（读不到 GitHub），引 Hardcodet.NotifyIcon.Wpf 之类社区库会引入还原风险。若后续确需气泡通知/现代菜单，再单独评估切库（记入 P2，不阻塞骨架）。

3. 状态灯语义（权威口径，纠正"三色 / 四色"的分歧）

PRD 里两处口径不同，以本 ADR 为准：

来源 表述 归属
§6.1.1 职责 4 绿=直连 / 黄=中继 / 红=离线（Adapter 只提供这三态） 阶段一
§6.4 四色：绿/黄/红 + 橙=授权异常 橙属阶段二（授权系统阶段一明确不做）

阶段一实现四态：绿=直连、黄=中继、红=离线、灰=已暂停（本地暂停态，由 pause/resume 决定，不需要授权信息）。 橙=授权异常只在枚举里留色位，阶段一不取值、不显示。

4. 进程边界与 IPC：阶段一不引入自定义 IPC

决定 - 引擎（syncthing.exe）以 Windows Service 身份运行；托盘假设"引擎服务已在跑、REST 在 127.0.0.1:8384"。 服务包装器 = shawl（依据：① 真机实测 sc.exe create 直接包 console 程序 → Start-Service 失败 CouldNotStartService； ② 上游 Bill-Stewart/SyncthingWindowsSetup 内部即用 shawl.exe，并用 asmt.exe 管服务账号）。落地归属见 §9 owner 表。 - 托盘进程内直接引用 LanSync.Syncthing 库调 REST，不自己起后台常驻、不发明命名管道/套接字协议。 - 托盘进程只做状态与配置，不持有文件句柄（PRD §6.9 P0）。

触发条件：将来若 Adapter 需要常驻进程（后台守护、跨用户会话访问），再单开 ADR-002 引入 IPC —— 现在做属于过度设计。

5. 配置与密钥位置

内容 位置 权限/纪律
引擎 home、引擎 config、引擎 API key %ProgramData%\LanSync\api-key.txt 安装器创建；ACL：SYSTEM+Administrators+服务账号完全控制、本机 Users 只读（托盘是普通用户进程，必须能读）。不得写日志、不得进仓库、不得进公开文档

6. 骨架范围（tzgj 线第一批交付）

  1. src/LanSync.Tray/LanSync.Tray.csproj：net10.0-windows10.0.17763.0（见 §1.1）；UseWPF；UseWindowsForms；SupportedOSPlatformVersion=10.0.17763.0；ImplicitUsings=disable（WPF+WinForms 同工程时，System.Windows / System.Windows.Forms / System.Drawing 的全局 using 会撞车 → Application、Brush 等 CS0104 歧义；改为显式 using + 别名）；引用 LanSync.Syncthing、LanSync.Core；加进 LanSync.sln

  4. 状态来源接 Adapter（LanSync.Syncthing）：连接类型 → 灯色；/rest/folder/errors → 冲突页签数据源
  5. 不实现：授权相关（橙）、自动更新、代码签名、真正的恢复写操作（面板先只读展示）

不含（别的线负责）：引擎 Service 注册（codex 线）、安装器/长路径 manifest/PS 5.1 脚本骨架（tzgj 线第二批）

7. 约束与验收

  • 禁止 Win11 专有组件（WindowsAppSDK、Mica、SnapLayout 等）；目标 Win10 1809 起
  • .ps1 含非 ASCII 必须带 UTF-8 BOM；用 PowerShell 5.1 语法
  • Directory.Build.props 已开 TreatWarningsAsErrors：构建零警告
  • 骨架验收：dotnet build LanSync.sln + dotnet format LanSync.sln --verify-no-changes 通过（功能完整度不要求）

8. 实现机环境前提（写给实现方）

  • 需要 .NET SDK 10.0.401（global.json 钉 10.0.401 + rollForward: latestPatch → 必须落在 10.0.4xx 带内；截至 2026-09-15，10.0.4xx 只有 10.0.400 与 10.0.401）
  • CI：Directory.Build.props 已设 EnableWindowsTargeting=true，因此 Linux runner 上也能构建含托盘的完整 sln（主线实测：dotnet build LanSync.sln 0 警告 0 错误、单测 22/22、无实例集成 2 passed/6 skipped、dotnet format --verify-no-changes 通过）。实现方在本机无需额外设置。

9. 引擎服务化细节（安装器落地用）

项 决定
包装器 shawl.exe（MIT），包 syncthing.exe serve --home %ProgramData%\LanSync\engine …
服务名 / 账号 服务名 LanSyncEngine；账号用虚拟服务账号 NT SERVICE\LanSyncEngine（不是 SYSTEM、也不再有口令）
账号权限 ① 虚拟账号无需"Log on as a service"、无口令（SCM 自动派生）；② 同步目录 Modify：icacls "<dir>" /grant "NT SERVICE\LanSyncEngine:(OI)(CI)M" /t；③ 卸载删服务即回收，无残留账号
账号决策依据 第二批实测暴露：原方案（随机口令建本地账号 LanSyncSvc → 口令即弃 → sc config obj= 无法完成，服务实际跑在 SYSTEM）是结构性缺陷。虚拟服务账号无口令可管、无需授予登录权限、卸载自动清理、权限面更小。边界：虚拟账号访问不了网络共享 ⇒ 阶段一同步目录限本机路径；将来要支持 UNC 再评估本地账号 + 凭据管理（另开 ADR）
依赖安装 安装器需检测 .NET Desktop Runtime 与 VC 运行库；缺失时提示并提供离线包路径
失败可见性 服务启动失败必须写入 %ProgramData%\LanSync\logs\install.log 并在安装器末尾显式提示（不能静默失败）

排障锚点：真机实验里"裸进程随 SSH 会话被杀""计划任务 LastTaskResult=1 起不来"两类失败都记录在 docs/M0.5-真机实验结论（Windows+跨网）.md。

10. 安装包与安装/卸载步骤（Inno Setup）

形态：单文件 .exe（Inno Setup），支持 /SILENT、/DIR=、/SYNCDIR=。

  1. 校验并落地 syncthing.exe（SHA-256 固定比对：v2.1.5 = 36a0f7bc…f50344）；落地 shawl.exe 与 LanSync.Tray.exe
  2. 创建 LanSyncSvc → 授予"作为服务登录" → 用 shawl 注册服务（参数见 §9）
  3. 生成 API key + 写配置（ACL 按 §5）
  4. 交互询问同步目录 → icacls 授权 → 起服务 → 托盘加开机自启（HKCU Run）
  5. 卸载：停服务 → 删服务 → 禁账号 → 删程序与配置 → 绝不删除任何用户同步目录（PRD §6.9）
  6. 代码签名：安装包与两个 exe 都需签名；证书来源属待项目发起人决策项（R10 的 P0），未签名前只在自己机器试装
  7. 开机自启不放在提权脚本里：安装器是提权上下文，写 HKCU\...\Run 会落到提升账号的配置单元。改为托盘首次启动时自写/自校验 HKCU Run（同用户上下文、幂等、可勾选关闭）；卸载时用 Inno 的 runasoriginaluser 步骤或托盘退出前清理。
  8. 卸载保留引擎身份：%ProgramData%\LanSync\engine\cert.pem、key.pem 决定 Device ID，删掉会让重装后变成"新设备"、对端要重新批准 ⇒ 默认保留身份两件套，删除 config.xml（folder 定义重装后重建）与 api-key.txt；提供 /PURGE 开关做彻底清除。
  9. 长路径：longPathAware 已声明在托盘进程 manifest（必须嵌入进程，故 src/LanSync.Tray/app.manifest 是唯一正确位置，packaging/ 不留副本——业经主线在构建产物 PE 里实测确认已嵌入）。引擎侧还依赖机器级 HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled：安装器检测该值，为 0 时在向导页明示并给"设为 1"复选框（默认勾选），结果写 install.log；不静默改机器级注册表。

11. 托盘 ↔ Adapter 接口边界

  • 托盘只调用 LanSync.Syncthing 暴露的方法，禁止自己发 Syncthing REST 请求（否则错误处理与授权口径会双份）。
  • 迭代 1 已具备（且通过零改动复核）：HealthAsync、配置安全更新（GET→改→PUT）、设备/文件夹/忽略规则、GetConnectionsAsync （映射 ConnectionKind.Direct/Relay/Offline/Unknown + paused）、SubscribeEventsAsync、Pause/ResumeAsync、GetFolderErrorsAsync（只读）。
  • C7 版本恢复事务已可用（2026-09-20 起）：RestoreVersionAsync 以降级语义支持无对端通道场景 （peerAdapters 可空；结果里 PeerPaused=false + UnpausedDevices 列出未暂停设备）。 ⇒ 托盘"恢复版本"面板解除只读，但必须按下面口径做 UI：
场景 返回值 UI 要求
全部对端被成功暂停 PeerPaused=true、UnpausedDevices 空 正常提示"已恢复到 <版本时间>"
拿不到对端通道（阶段一常态） PeerPaused=false、UnpausedDevices 非空 必须显式警示"对端未暂停，若其在线可能产生冲突副本"，并列出设备名

禁止把 PeerPaused=false 当成功静默处理——这是实测过的静默数据覆盖风险（adapter/exp_restore.py、C7 负例）。 真正的对端暂停能力见 docs/ADR-002-对端暂停控制通道.md（阶段二，复用引擎证书的 LAN 控制端点 + 租约自愈）。 - 尚不可用（其余）：无。控制通道属阶段二，不阻塞面板上线。 - 状态灯映射见 §3（四态 + 橙留位）。

14. 第二批复核结论 → 第三批要求（tzgj 线，2026-09-15 · 已交付并复核通过）

第三批交付：分支 tzgj/tray3（commit 36626bc），已合入 main。主线复核：构建 0 警告 0 错误、format、 四条静态检查、三个含中文脚本 BOM、隐私扫描、作者身份均通过；§14 七项逐条对上（虚拟账号 sc config obj= 无 password、 API key ACL、Runtime 检测、自启搬托盘 AutoStart.cs、长路径向导页、卸载保身份 + /PURGE、publish 产物）。 遗留见 §15。

主线复核（合入 95595cc 前）：构建 0 警告 0 错误、format 通过、四条静态检查通过、隐私扫描干净、 syncthing.exe SHA-256 常量与 M0.5-真机结论 记录逐位一致、app.manifest 已确认嵌进进程 PE。 以下为复核发现，属第三批范围：

  1. 服务账号落地（结构性缺陷修复）：现 install.ps1 随机建账号 LanSyncSvc 后丢弃口令，sc config obj= 又未接 ⇒ 服务实际跑在 LocalSystem、目录 ACL 白授。 改为虚拟服务账号：删掉建账号/口令/secedit 逻辑，注册后执行 sc.exe config LanSyncEngine obj= "NT SERVICE\LanSyncEngine"（无 password 参数），目录 ACL 改授 NT SERVICE\LanSyncEngine。
  2. API key ACL：icacls api-key.txt → SYSTEM/Administrators 完全控制、NT SERVICE\LanSyncEngine 读、本机 Users 只读（§5）。
  3. 依赖检测收口：.NET Desktop Runtime 精确检测（扫 %ProgramFiles%\dotnet\shared\Microsoft.WindowsDesktop.App\10.*），缺失时给出离线包路径并要求确认。

  5. 长路径检测：安装向导检测 HKLM\...\FileSystem\LongPathsEnabled，为 0 时明示 + 复选框设为 1（默认勾选），结果写 install.log；不静默改机器级注册表。
  6. 卸载保身份：保留 engine\cert.pem、key.pem（Device ID 稳定），删 config.xml 与 api-key.txt；新增 /PURGE 彻底清除开关。
  7. 安装源改 publish 产物：setup.iss 的 [Files] 取 dotnet publish -c Release -r win-x64 输出并同步进 packaging\bin，不再引用源码树的 bin\Release\... 路径。
  8. 保持不动的：AppId 当前 GUID（改则升级识别断裂）、卸载绝不删用户同步目录、失败必须写 install.log。

15. 第三批复核发现 → 第四批要求（tzgj 线：真实安装测试，2026-09-15）

主线复核（合入前）发现一处会在自己机器上立刻踩到的缺陷，加三项"必须实跑"的验证：

  1. Runtime 检测有假阴性：Test-DotnetDesktopRuntime 只扫 %ProgramFiles%\dotnet\shared\Microsoft.WindowsDesktop.App。 用户级安装（dotnet-install 默认落 %USERPROFILE%\.dotnet）与 dotnet --list-runtimes 都覆盖不到 ⇒ 在装了用户级 SDK/Runtime 的机器上会误判缺失并阻断安装（tzgj 自己那台正是用户级 10.0.401）。 改法：优先 dotnet --list-runtimes（PATH 上有 dotnet 时），否则同时扫 %ProgramFiles%、%ProgramFiles(x86)%、 %USERPROFILE%\.dotnet 三处；仍找不到才阻断。
  2. Inno 必须真编译：本机装 Inno Setup（winget install -e --id JRSoftware.InnoSetup；无管理员权限时用 innosetup-6.7.1.exe /VERYSILENT /CURRENTUSER），跑 iscc packaging\setup.iss 直到零错误。 重点验 [Code] 与 [UninstallRun] 里未实跑的写法：{code:GetPurgeSwitch} 与 {param:SYNCDIR} 在卸载上下文的行为 （若卸载侧不支持 {code:}/{param:}，就退化为"忽略 /PURGE"，方向安全但要写进注释）。
  3. 在 Win10 开发机上做一次真实安装 + 卸载（这正是兼容性文档里"Win10 真机缺位"的补位动作）： - 先记录 winver 版本与 HKLM\...\FileSystem\LongPathsEnabled 初值 - 装：LanSync-Setup-x.y.z.exe /SILENT /SYNCDIR=D:\LanSyncTest（同步目录必须用测试目录） - 验：sc qc LanSyncEngine（账号应为 NT SERVICE\LanSyncEngine）、sc query（Running）、 目录 ACL（icacls）、api-key.txt ACL、%ProgramData%\LanSync\logs\install.log 内容、 托盘首启写入 HKCU\...\Run 且菜单可关闭 - 卸：先默认卸载（engine\cert.pem/key.pem 必须仍在），再用 /PURGE 卸载（全清）；两次都确认同步目录未被删 - 全程贴命令与输出到 status.md（这是"实测"，不是"应该"）
  4. 引擎二进制：主线把 syncthing.exe（v2.1.5，SHA-256 36a0f7bc…f50344）与 shawl.exe 放到交付台， tzgj 下载进 packaging\bin\，先自行核对 SHA-256（install.ps1 运行时也会比对），再编译安装包。
  5. publish 一致性：确认 packaging\publish.ps1 产出的 bin\tray\* 与 setup.iss 的 [Files] 完全对得上 （含 LanSync.Tray.exe、依赖 dll、app.manifest 内嵌情况）。
