# M0.5 技术基线 PoC 操作手册 v0.3

> 配套：《局域网同步系统-产品文档-v0.9（rc）》
> 目标：**不写产品 UI、不写授权、不写数据库**，用原生 Syncthing + 自建 `stdiscosrv` + 私有 `strelaysrv`，把阶段一技术基线跑实。
> M0.5 结束必须产出：① 五项基础能力结论 ② E2–E6 实测报告 ③ 版本锁定表 ④ §13/§14/§15 回填项 ⑤ v1.0 冻结结论。
>
> **v0.3 相对 v0.2**：本机真机实验（Syncthing v2.1.5 + 自建 disco/relay，见 `adapter/`）推翻了 7 处，逐条已在 §16 标注。
> 其中 **2 处是 v0.2 自己写错的方向**：① relay 的 URI 其实**默认就会打印**（只有 ID 需要 `-debug`）；
> ② `bytesProxied` 实测 ≈ 转发单向字节量（8 MiB → 8.02 MiB，**1.00×**），v0.2 写的"要除以 2 / 会高估一倍"**是错的**。

## 0. 本轮纪律

1. **只做 PoC，不顺手开发产品功能。** 不写托盘、不写 Adapter 正式代码、不做 License、不做后台。
2. **服务端先不套 Caddy/443。** M0.5 直接让 `stdiscosrv` 监听 8443、`strelaysrv` 监听 22067；基线确认后 M2 再决定映射 443。
3. **关闭 Syncthing 自动升级。** 所有客户端进程都带 `--no-upgrade`。
4. **关闭官方 discovery / public relay。** 只允许自建 `stdiscosrv` 与私有 `strelaysrv`。
5. **测试目录必须是专用目录。** 不拿真实工作底稿做破坏性测试。
6. **所有命令输出都留档。** 统一目录 `M05-YYYYMMDD/`，每个实验一个子目录。

### 0.6 停工条件（v0.2 新增：出现这些就停下来上报，不要"接着跑完再说"）

| 编号 | 触发条件 | 动作 |
|---|---|---|
| STOP-1 | E3 出现**静默丢文件**（一端文件消失且另一端不知道） | **立即停 M0.5**，保留现场（两端目录 + `.stversions` + Syncthing 日志），先定位 |
| STOP-2 | E3 出现**大小写同名互相覆盖**导致内容被替换 | 立即停，保留同名文件的两个版本与时间线 |

| STOP-5 | 测试期间误用了真实工作目录 | 立即停，先确认未产生数据事故 |

## 3. ECS 基线部署

### 3.1 生成 relay token

```bash
openssl rand -hex 32
sudo install -d -m 700 /opt/lan-sync/m05/secrets
sudo sh -c 'printf "%s" "<RELAY_TOKEN>" > /opt/lan-sync/m05/secrets/relay-token'
sudo chmod 600 /opt/lan-sync/m05/secrets/relay-token
```

报告中只写 `TOKEN_SET=yes`，**不要粘贴 token**。

### 3.2 启动 `stdiscosrv`

> **v0.2 修正**：`--db-dir` 的语义是**目录**（help 文本 "Database directory"，默认 `.`）。
> v0.1 写的 `--db-dir=/var/stdiscosrv/discovery.db` 会让数据库落到 `/var/stdiscosrv/discovery.db/discovery.db`，是一个隐藏坑。

```bash
sudo mkdir -p /opt/lan-sync/m05/disco

docker run -d \
  --name m05-disco \
  --restart unless-stopped \
  -p 8443:8443/tcp \
  -v /opt/lan-sync/m05/disco:/var/stdiscosrv \
  lansync/stdiscosrv:v2.1.5 \
  --listen=:8443 \
  --db-dir=/var/stdiscosrv
```

```bash
docker logs m05-disco --tail 100      # 记下 deviceId（v0.3 附注：stdiscosrv 没有 -version，查版本用 -v）
docker ps --filter name=m05-disco
ss -lntp | grep 8443
```

第一次启动会生成 `cert.pem` / `key.pem`（落在卷里，重启不丢身份）。把日志里的 **`deviceId`** 记为 `<DISCO_SERVER_ID>`，客户端用它做证书固定。

### 3.3 启动私有 `strelaysrv`（含 ID 获取的修正）

> **v0.3 纠正（真机实测）**：
> - **URI 默认就会打印**（`main.go:270` 无条件执行）——v0.2 说它只在 `-nat` 下打印，**是错的**；
> - **只有 `ID:` 那一行在 `if debug` 内**（`main.go:191-193`）——所以 v0.2 让你"用 `-debug` 抓 URI"属于绕远路；
> - 最省事：默认日志里的 URI 已经含 `id=<RELAY_DEVICE_ID>`，**取它 + 追加 `&token=<RELAY_TOKEN>`** 就是客户端地址。

```bash
sudo mkdir -p /opt/lan-sync/m05/relay
RELAY_TOKEN="$(sudo cat /opt/lan-sync/m05/secrets/relay-token)"

# 取 ID/URI：默认日志里【已经有 URI】（源码 main.go:270 无条件打印），
# 直接把它拿来用即可；若还想看到 "ID: ..." 那一行，才需要 -debug（main.go:192 在 if debug 内）。
docker logs m05-relay 2>&1 | grep -m1 'URI:'      # 形如 relay://host:22067/?id=<RELAY_DEVICE_ID>&networkTimeout=...
# 一次性 -debug（可选，仅为多拿一行 ID）
docker run --rm -v /opt/lan-sync/m05/relay:/var/strelaysrv lansync/strelaysrv:v2.1.5 \
  -pools="" -token="$RELAY_TOKEN" -keys=/var/strelaysrv -listen=:22067 -status-srv=:22070 -debug 2>&1 | head -40

# 正式启动（去掉 -debug）
docker run -d \
  --name m05-relay \
  --restart unless-stopped \
  -p 22067:22067/tcp \
  -p 127.0.0.1:22070:22070/tcp \
  -v /opt/lan-sync/m05/relay:/var/strelaysrv \
  lansync/strelaysrv:v2.1.5 \
  -pools="" \
  -token="$RELAY_TOKEN" \
  -keys=/var/strelaysrv \
  -listen=:22067 \
  -status-srv=:22070
```

```bash
docker logs m05-relay --tail 60
curl -s http://127.0.0.1:22070/status | python3 -m json.tool
ss -lntp | grep -E '22067|22070'
```

**客户端 relay URI（拿上面的 URI 直接追加 `&token=`）**：

```text
relay://<RELAY_HOST>:22067/?id=<RELAY_DEVICE_ID>&token=<RELAY_TOKEN>
```

> `-pools=""` 与 `-token` 都会让 relay 退出公共池（这一点 relay 启动日志里有显式警告确认）。
> `-keys=/var/strelaysrv` 与 Dockerfile 的 `WORKDIR`/`VOLUME` 一致，显式写出来是为了防止上游改 Dockerfile 后身份文件跑到卷外。

### 3.4 安全组 / 防火墙（v0.2 收紧）

| 端口 | 是否开放 | 来源限制 |
|---|---|---|
| 8443/TCP | 开放 | 建议限制为家庭/公司出口 IP（§0.5 P9 记录）；至少不要对 0.0.0.0/0 长期开放 |
| 22067/TCP | 开放 | **M0.5 期间限制来源 IP**（或临时换非默认端口）——因为共享 token 是"门禁卡不是身份证"，泄漏后无法按设备追责 |
| 22070/TCP | **不开放** | 只从 ECS 本机 `curl 127.0.0.1:22070/status` 读取 |

跑完 M0.5 后按 §15 恢复安全组。

## 4. Windows 客户端初始化

A/B/C/D 各自建立独立 Home：

```powershell
New-Item -ItemType Directory -Force C:\LanSync\m05\home | Out-Null
New-Item -ItemType Directory -Force C:\LanSync\m05\sync | Out-Null

$ApiKey = [guid]::NewGuid().ToString('N')
```

打开本机 GUI（默认 `127.0.0.1:8384`）完成配置：

1. **Local Discovery：开启**。
2. **Global Discovery：开启，但删掉 `default`，只填自建**：

```text
https://<DISCO_HOST>:8443/?id=<DISCO_SERVER_ID>
```

3. **Relay：只使用私有 relay。** Sync Protocol Listen Addresses 保留本机 TCP/QUIC，并加入：

```text
relay://<RELAY_HOST>:22067/?id=<RELAY_DEVICE_ID>&token=<RELAY_TOKEN>
```

4. 删除公共 relay 的动态地址 / `default` 项。
5. 远端设备地址保持 `dynamic`。
6. 建本轮专用 Folder（A/B/C 共享）；启用 **Staggered Versioning，保留 30 天＝`maxAge = "2592000"`（⚠️ 单位是秒）**。
7. 设置 `.stignore`：只放本轮明确忽略项（`~$*`、`.~lock.*`、`Thumbs.db`、`.DS_Store`），**不要**默认忽略 `.git` / `node_modules` / `*.tmp`。
8. **用 REST 生成文件夹配置时注意类型（v0.3 实测）**：`versioning.params` 的值必须是**字符串**，
   `{"maxAge": "2592000"}` ✅（值必须是**字符串**，且 `maxAge` 的单位是**秒**——写 `"30"` 只保留 30 秒）；传数字会得到 `HTTP 400 cannot unmarshal number into ... of type string`
   （源码：`lib/config/versioningconfiguration.go` 里 `Params map[string]string`）。顶层 `cleanupIntervalS` 反而是 int。

# 5. 五项基础能力验证

## B1：双机原生同步

A/B 同一局域网互加 Device ID，Folder 双向共享。

```powershell
Set-Content C:\LanSync\m05\sync\hello.txt "m05 $(Get-Date -Format o)"
```

**PASS**：B 出现相同文件；新增/修改/删除/重命名最终一致。

## B2：自建 discovery 生效

保持 A/B/C 的 Global Discovery 只有自建地址。

```bash
docker logs m05-disco --since 10m
```

**PASS**：能看到客户端向自建 discovery announce/query；客户端不依赖官方 discovery。

## B3：私有 relay + token 生效

先确认正确 token 能连；再在 D 上故意用错误 token。

**PASS**：正确 token 可加入私有 relay；错误 token 无法加入。**这里验的是「Relay 使用准入」，不是文件访问权限**——另需确认"未互加 Device ID 的设备即使持有 token 也看不到任何文件"（同步成员准入）。

## B4：LAN 直连 / WAN relay 自动回落

A/B 同网读 `/rest/system/connections` 记类型；然后 A/C 跨网重复。

**PASS**：LAN 以 `tcp-*`/`quic-*` 直连为主；跨网不能直连时自动出现 `relay-*`，无需人工切换。

## B5：版本历史 / Restore API

先在 A 建 `restore-test.txt`，确保同步到 B；再由 A 修改或删除，使 **B** 产生远端变更归档（versioning 只在"远端变更替换/删除本地文件"时归档，本机自己删的不算）。

```powershell
Invoke-RestMethod -Headers $H "http://127.0.0.1:8384/rest/folder/versions?folder=<FOLDER_ID>"

$Body = @{ 'restore-test.txt' = '<VERSION_TIME>' } | ConvertTo-Json
Invoke-RestMethod -Method Post -Headers $H -ContentType 'application/json' `
  -Body $Body "http://127.0.0.1:8384/rest/folder/versions?folder=<FOLDER_ID>"
```

**PASS**：B 恢复成功；恢复后的文件作为正常本地变更重新同步到其它设备。

> ⚠️ **必须按三步走（v0.3 实测）**：`暂停对端连接 → 恢复 → 恢复连接`。
> 不暂停对端时，对端的较新版本会在 1–2 秒内把恢复结果**覆盖回去**，而 `POST /rest/folder/versions`
> **返回的是成功**（空字典）——属于静默失效。对照实验见 `adapter/exp_restore.py` 与 `local-lab/exp-restore.json`。
> 另：返回体是"每文件一条错误"的字典，**必须判空**，不能只看 HTTP 200。

- RSS 随连接建立上升后基本稳定 → PASS
- RSS 随已传字节持续线性上涨且不回落 → FAIL，查缓冲/泄漏
- OOM / 容器被杀 → FAIL（并按 §0.6 STOP-3 处置）

## E2-D：实际 relay 吞吐（v0.2 加了口径说明）

```bash
curl -s http://127.0.0.1:22070/status > /tmp/relay-before.json
# ★ 此时开始真实大文件 relay 传输，记录起止时间（date +%s）
curl -s http://127.0.0.1:22070/status > /tmp/relay-after.json
```

```text
双向合计吞吐 Mbps = (after.bytesProxied - before.bytesProxied) × 8 / 秒数 / 1,000,000
```

> ⚠️ **长传吞吐 = 上一个式子直接算**（`bytesProxied` 单位是字节）。
> **关于"双向"的纠正（v0.3 实测）**：`bytesProxied` 统计的是"两个方向的转发量之和"，但**每个字节只被写出去一次**，
> 所以 **relay 的实际转发量 ≈ bytesProxied，不需要除以 2**。实测：8 MiB 不可压缩文件经 relay →
> `bytesProxied` 增量 **8,414,742 字节 = 8.02 MiB（1.00×）**，A 侧 `outBytesTotal` 增量 8.00 MiB。
> ⇒ **成本 ≈ bytesProxied × 单价**；真正的"倍数"来自**接收端数量**（一个改动发给 N 端 = N × 大小）。

# 8. E4：真实中继出流量 + 跨网直连率

## E4-A：正常模式

A/C 分属不同网络，direct 与 relay 都可用。做 20 次小/中文件变更，每次读 `/rest/system/connections`，按 `type` 分类：

```text
direct 次数 = N_direct     （tcp-* / quic-*）
relay 次数  = N_relay
观测直连率 p = N_direct / (N_direct + N_relay)
```

**这只是观测值，不设硬门槛。**

## E4-B：强制 Relay，核对字节数（v0.2 换了做法）

> **v0.1 用防火墙 Block 22000/TCP+UDP，逻辑有效（Windows 防火墙 Block 优先于 Allow），但改动面大、容易忘删。**
> **v0.2 首选：临时把 listen address 里的直连项去掉，只留 relay。**

在两端（A/C）的 Sync Protocol Listen Addresses 中，临时把 `tcp://0.0.0.0:22000` 与 `quic://0.0.0.0:22000` **删掉**，只保留 relay URI；
**并且必须确认 `Options.RelaysEnabled = true`**（v0.3 实测：置 false 时 `relay://` listen 地址**完全不生效**，日志里不会出现 Relay listener），
然后再 `POST /rest/system/restart`（**只改地址不重启无效**：已建立的直连不会断）。
等 `/rest/system/connections` 的 `type` 变成 `relay-*` 后再传已知大小的真实文件。测完**把 listen address 改回原样并重启**。

> 备选（如果必须验证"网络层真的不通"）：才用防火墙法，并在测完立即删除规则。

```powershell
# 备选方案（用后必须删）
New-NetFirewallRule -DisplayName 'M05 Block ST TCP 22000' -Direction Outbound -Protocol TCP -RemotePort 22000 -Action Block
New-NetFirewallRule -DisplayName 'M05 Block ST UDP 22000' -Direction Outbound -Protocol UDP -RemotePort 22000 -Action Block
# ...测完...
Remove-NetFirewallRule -DisplayName 'M05 Block ST TCP 22000'
Remove-NetFirewallRule -DisplayName 'M05 Block ST UDP 22000'
```

数据采集（ECS）：

```bash
curl -s http://127.0.0.1:22070/status | tee /tmp/e4-before.json
# 传文件
curl -s http://127.0.0.1:22070/status | tee /tmp/e4-after.json
```

同时记录客户端侧 `outBytesTotal` / `inBytesTotal`。

**PASS**：`bytesProxied` 增量与客户端实际传输量同一量级（实测为 **1.00×**，偏差 ≤30% 记 PASS）。
**成本口径（v0.3 纠正）**：**直接用 `bytesProxied` × 单价**即可 —— 每个转发的字节只出网一次，
不必除以 2，也不存在"高估 2 倍"的问题（v0.2 的说法已作废）。计费口径请用客户端侧 `outBytesTotal` 交叉验证。

## E4-C：回填成本公式

```text
中继出流量（单向）≈ 跨网改动量 × (1 - p) × 接收端数量
全中继悲观上界     = 跨网改动量 × 1 × 接收端数量
```

两个都写进报告：用实测 `p` 算预期，保留 `p=0` 作为上界。
