0. 本次对原始需求的完善清单

原始需求给了三个主干（局域网同步 / 云中转 / 云端授权）。以下是补齐后必须一并定义的部分，越靠前越是"不做就要返工"的：

# 补充项 为什么必须补 优先级
1 冲突与删除语义 同步软件最容易"丢数据"的地方，不是网络而是并发写和删除 P0
2 授权失效的降级策略（离线宽限期） 只写"授权在云上"会做出一个"断网就罢工"的软件，工作场景不可接受 P0
3 中继流量成本模型与配额 阿里云公网出流量 0.8 元/GB，中转跑量的成本会超过服务器本身，直接决定商业模式 P0
4 防破解的关键点：把能力锁在服务端 客户端本地授权校验必然可被绕过；只有"中继 Token 必须由服务端签发"才是真正不可绕过的闸门 P0
5 设备指纹与换机/解绑策略 授权按设备卖，就必须定义"什么算一台设备""换硬盘算不算" P0
6 跨平台文件系统语义 中文/emoji/超长路径/大小写/软链/Office 锁文件，是同步事故高发区 P0
7 账号体系与权限模型（角色、文件夹级 ACL） "授权"是商业许可，"鉴权"是人/设备身份，两者必须分开设计 P0
8 文件版本历史与回收站 用户对"同步"的真实期待是"能找回"，不只是"能对上" P1
9 管理后台与审计日志 有授权就有吊销、有配额就有看板，没有后台运营会瞎 P1
10 选择性同步 / 忽略规则 20GB+ 工作目录不可能全部下发到每台设备 P1
11 自动更新 + 代码签名 没有签名的监听文件型程序会被杀软/EDR 拦，分发不下去 P1
12 合规面：软著、隐私政策、数据出境 若对外销售则必有；自用可后置 P2

1. 产品定位（一句话）

给小型团队/个人工作室的一套私有文件同步系统：同一局域网内设备之间点对点直连秒同步；一旦不在同一网段，自动经自有阿里云服务器加密中转继续同步；授权（License）与身份鉴权全部由自己掌控，可签发、可计量、可吊销。

与现成产品的差别（卖点）：数据通道自建、授权不依赖第三方、局域网内网速跑满且不产生云流量费。

2. 背景、目标与非目标

2.1 背景痛点

  • 现有网盘（百度/坚果云/OneDrive）在同一办公室里也要绕公网一圈，大文件慢、且按量计费。
  • 现成同步工具（Syncthing/Resilio）要么无中心授权（管不住设备和许可），要么授权在别人手里。
  • 工作文件（审计底稿、报表、扫描件）体量大、含敏感信息，不适合第三方云。

2.2 业务目标（可量化）

编号 目标 指标
G1 局域网可用性 同网段设备发现成功率 ≥ 95%，变更到对端可见 P95 < 3s
G2 跨网可用性 跨网自动建立连接、无需用户操作：能直连则优先直连，无法直连自动回落私有 relay。跨网直连率作为观测指标（E4/E6 记录），不作阶段一硬门槛——只有公司/家里几个网络，百分比统计意义很弱
G3 数据安全 同步过程中不丢文件、不静默覆盖；冲突 100% 保留双方副本
G4 授权可控 新增/续期/吊销授权生效时间 ≤ 5 分钟（在线设备）
G5 成本可控 中继流量可计量、可配额、可告警，单租户月流量可设硬上限

2.3 非目标（明确不做，避免范围膨胀）

  • 不做在线协同编辑（不是 OnlyOffice/飞书文档）
  • 不做 Git 式的分支/合并语义（是文件同步，不是版本控制系统）
  • v1 不做移动端、不做 Web 端上传下载门户
  • 不做跨租户文件分享链接

2.4 实施阶段划分（2026-09-13 决策）

阶段 目标 包含 不包含 出口标准
阶段一：主体（先做这个） 「装完就能同步」——局域网直连 + 跨网自动中转 Syncthing 原生引擎 + 局域网发现 + 跨网发现与中继回落 + 冲突与版本恢复（用原生能力）+ 客户端托盘 + Windows 打包 授权系统、账号登录、管理后台、自研 signaling、动态 relay Token、多租户数据库、商业计量计费 4 台设备（公司 2 + 家里 1 + 测试机）连续 2 周无数据事故

阶段一的设备准入方式（关键设计，v0.7 定稿）：

Windows 客户端 → 原版 Syncthing → 私有 strelaysrv -pools="" -token=<secret>

即 共享 -token（上游原生能力，一个配置项）——阶段一不改 relay、不写授权、不写鉴权协议。 ⚠️ 之前写的"relay 侧静态 Device ID 白名单"上游并不存在（源码实测见 §12.4），已作废。 阶段二再单独立 ADR 决定：A. 保持原版 relay + 共享 token，放弃 relay 层单设备即时吊销； B. fork/patch strelaysrv 增加"Device ID + 服务端授权"准入层（W1/W2）。选了"≤5 分钟吊销"就等于选了 B。

⚠️ 阶段一有两层完全不同的「准入」，不要混为一谈（v0.9 明确）

层 机制 管什么 谁能决定
① 同步成员准入 双方在 Syncthing 里互加 Device ID 并共享同一个 Folder 谁能看到/改文件 你（在客户端里加/删设备）
② Relay 使用准入 持有私有 strelaysrv 的共享 -token 谁能占用中继带宽 token 的持有者

关键：relay 只是传输通道，拿到 relay token ≠ 获得文件访问权——文件访问权只由①决定。 反过来，① 也不能保护你的账单（中继带宽是②的事）。两层各自独立。

⚠️ 共享 -token 的威胁模型（v0.8 补写，必须知道）

项 事实
它保护什么 只保护 relay 资源不被陌生人蹭用——它不识别设备，不是身份凭证
谁能用 任何拿到这个字符串的 Syncthing 都能占用你的中继带宽（含被复制到别的机器）
能否按设备追责 不能。泄漏后无法定位是哪台设备在用，也无法只封某一台
能否按设备限速 不能（只有 -per-session-rate / -global-rate 这类全局限制）
缓解措施 ① token 只发给自己人；② 定期轮换（改配置 + 重启 relay）；③ 靠打洞优先让流量尽量不过中继；④ 云监控预算告警；⑤ 阶段二 W1 升级为按设备准入

一句话：-token 是"门禁卡"，不是"身份证"——这正是 §12.4 里 W1（逐设备准入）存在的理由。

关于流量：两个概念必须分开（v0.7 修正 v0.6 的自相矛盾）

概念 阶段一 阶段二
技术流量监控（防止账单失控） ✅ 做，但只能到全局粒度：relay /status 的 bytesProxied + 云监控账单告警 保持
商业计量计费（按设备/按人算钱） ❌ 不做 需要 W2（改中继转发层）才有的按设备归属

⚠️ v0.6 曾写"阶段一 relay_usage 按 Device ID 记录字节数"——这与上游能力冲突，已删除。 阶段一能拿到的只有全局数字。

5. 关键场景（用户故事 + 验收要点）

U1 办公室内多机同步 财务组 3 台电脑共享 D:\工作底稿（约 20GB，含 5 万个文件）。首次全量各自跑满千兆内网；之后改动一个 Excel，另两台 3 秒内可见。 验收：首次同步不经公网（服务端流量为 0）；未改动文件不重传。

U2 出差/在家 在家打开笔记本，局域网里没有同伴，客户端 5 秒内自动切到阿里云中继，继续收改动，用户无感、无需手动切换。 验收：切换过程不中断、不重复下载已完成部分；状态灯由"直连绿"变"中继黄"。

U3 断网 8 小时 地铁/断网期间本地改动照常落盘；恢复网络后自动补齐，已传块不重传，不产生冲突副本。 验收：断网期间的多次保存只同步最终状态，中间态不产生垃圾文件。

U4 授权到期 / 超设备数 客户 License 到期前 7 天开始提示；到期后进入 14 天宽限期（功能正常）；宽限期满后按策略降级（只读或停止同步），绝不静默失效或删数据。

U5 离职设备吊销 管理员后台点"吊销"，在线设备 5 分钟内停止同步并提示"授权已被管理员收回"；离线设备下次联网即失效。

U6 完全隔离内网（无公网） 内网无外网出口时，用离线授权文件（.lic）导入激活，功能完整，仅不做在线心跳（以离线文件有效期为准）。

U7 双端同时改同一文件 A、B 两台设备在断网期间各自改 报表.xlsx。恢复后不互相覆盖：Syncthing 会把较早修改时间的那个重命名为原生冲突文件 报表.sync-conflict-20260913-142200-B设备名.xlsx（磁盘上保持原生命名，不自定义，§FR-3.2），并在托盘 UI 的「冲突」列表里显示为「报表.xlsx — 与设备 B 冲突 — 2026-09-13 14:22」，可一键打开比较。

U8 误删恢复 成员误删整个文件夹并已同步扩散。⚠️ 这是"版本历史"而不是"全局回收站"（v0.9 更正）：Syncthing 的版本归档是按设备、按 Folder 配置的，且只在「远端变更导致本地文件被替换/删除」时才归档旧版本，默认还是关闭的。阶段一决定：启用 Staggered versioning，maxAge = 30 天（§FR-3.3）——因此"能恢复到哪一版"取决于该设备确实归档过哪些版本，不能承诺从任意设备恢复任意版本。

9. 关键流程

9.0 阶段一：设备入网与连接（无授权，先保证主体）

  1. 各端首次运行 → 生成 Syncthing Device ID（= 设备证书指纹）→ 客户端显示短码 / 二维码
  2. 任一端的「添加设备」里输入对方短码（或扫码）→ 双方互相接受 → 建立互信（互加 Device ID）
  3. 跨网互通：不存在"登记进 relay 白名单"这一步——relay 侧只配一个共享 -token（全体客户端共用同一个字符串），所有客户端带上它即可连接（§12.4；逐设备 ACL 是 W1 工作项，属阶段二）
  4. 之后全自动：同网段走局域网直连（§9.3），不同网段自动走中继（§9.4）

阶段一没有「激活」这一步，也没有 License 校验；能让设备加入的只有「手工互加 Device ID」＋「持有 relay 的共享 -token」两件事。 这在自己人小范围共用的前提下可接受（D1 决策）；放开使用范围或对外时，必须先上阶段二的授权体系。

9.1 激活（阶段二）

  1. 客户端首次启动 → 生成本机指纹 → 弹激活窗（输入 License Key 或导入 .lic）
  2. 联网：POST /v1/license/activate → 服务端校验租户/席位/设备数/状态 → 返回签名 Blob（含 not_after、grace_days、features、issuer、nonce）
  3. 客户端内置公钥验签 → 存本地 → 进入正常同步
  4. 离线：管理员在后台导出 .lic（内含该设备指纹）→ 手工导入

9.2 心跳与吊销

每 24h 上报 POST /v1/license/heartbeat，携带 Blob 版本 + 上次服务端时间戳。防雪崩与失败处理： - 正常 → 返回 200 + 新 Blob（如续期） + 一批中继凭证（见 FR-4.12），客户端刷新本地有效期 - 已吊销 → 403 revoked → 立即停同步 + 弹窗明示（不静默） - 不可达 → 进入宽限倒计时（本地记录连续失败次数与时长）；重试采用指数退避 + 恢复期随机错峰窗口（替代原"±10% 抖动"，R6′） - 服务端连续 5xx → 客户端静默重试，但静默窗口 ≤ min(心跳间隔 × 3, 宽限期剩余时长 × 20%)； 超限必须弹窗告知"授权服务不可达，已进入宽限期"——与 FR-4.11"绝不静默降级"对齐（R6′）

9.3 连接建立（全程 Syncthing 原生，v0.9 整节重写）

阶段一不设计任何自研网络协议：没有自研 mDNS 服务、没有 workspace 广播、没有自研 signaling、没有自研打洞。 下面写的是"原生流程长什么样"，供理解，不是要实现的东西。

局域网内（同网段）

Syncthing → 原生 Local Discovery（UDP；IPv4 用广播 255.255.255.255、IPv6 用多播 ff12::8384，端口 21027）
          → 获知对端 Device ID + 地址 → 直接 TCP/QUIC 连接

⚠️ 更正：早期文档写的「多播组 239.x.x.x:50000 / mDNS _lansync._udp / workspace_id 广播」全部作废—— 那是自研方案的残留，与原生 Local Discovery 不是一回事。

跨网（不同网段）

Syncthing → 查询自建 stdiscosrv（替代官方 global discovery）
          → 尝试原生直连（含 UPnP / NAT-PMP 端口映射与 hole punching）
          → 仍无法直连 → 自动回落到自建私有 strelaysrv

NAT 穿透能力由 Syncthing 原生提供，阶段一不自己实现打洞。

为什么这样最简单：以上全部是 Syncthing 的既有行为，阶段一要做的事情只有三件—— ① 关掉官方 discovery/relay；② 把 stdiscosrv / strelaysrv 地址写进客户端配置；③ 给 relay 配共享 -token（§2.4）。

9.4 中继回落

  1. 中继凭证由授权服务在心跳时批量预签发（单张 ≤ 1 小时，一批 24 张），客户端缓存消费； claims 绑定 Syncthing Device ID（= 设备证书指纹）
  2. 携带凭证连 relay 节点 → relay 核对握手 TLS 证书指纹与凭证声明一致（凭证被提取也无法在其它设备使用）→ 只做密文转发与计量 → 不解析内容
  3. 授权服务向 relay 推送已吊销 Device ID 黑名单 → 吊销在中继层即时生效（满足 G4 ≤5 分钟）， 不必等凭证自然过期
  4. 授权服务短时不可达 → 消费缓存凭证继续中转；缓存耗尽且已达 FR-4.7 宽限期上限 → 按策略降级

阶段一的差异（v0.6 更正）：第 1–3 步换成「客户端携带共享 -token 即可连接」——这是上游原生能力、零代码。⚠️ 原先写的"relay 侧静态 Device ID 白名单"与"按设备记录字节数"在上游并不存在（源码实测：无白名单/黑名单，bytesProxied 是全局计数器），二者属于改造工作项：W1＝逐设备准入白名单、W2＝逐设备流量计量（§12.4）。阶段一先接受「共享 token + 全局流量监控」的粗粒度形态。

9.4.1 准入适配层（阶段一 / 阶段二共用同一抽象）

第二轮评审建议：把"准入"做成可插拔接口——这样 D7 的"授权后置"才是真的后置， 而不是将来把准入逻辑重写一遍。

阶段 实现 内容 代码量
阶段一 AllowlistAdapter 上游原生：共享 -token（一个配置项） ~0（配置）
阶段一+ AllowlistAdapter（逐设备版） W1 改造后的白名单 + 黑名单校验 W1 工作量
阶段二 CredentialAdapter 授权服务签发凭证（绑定 Device ID）+ relay 侧校验 + 吊销黑名单推送 R2′ 工作量

CheckJoin(deviceID, credential) -> allow | deny(reason)

凡"转发逻辑"以外的判断一律走这两个钩子 ⇒ 换准入方式时只替换 adapter，不动转发层。

授权强度 可写进协议层（无有效 License 则握手失败），技术层面最硬 授权在外层实现（启动前校验、自有中继凭证、成员准入、配置下发）：合规与管理层面可控，但挡不住用户绕过客户端直接跑原版 Syncthing（诚实说明：对"自用+小团队、自己就是发行方"完全够用；对外卖则强度不足）
许可与合规 无第三方许可约束 MPL-2.0：闭源集成 OK，只有改动其源文件才须公开该文件；不用它的官方发现/中继服务器，改用自建的即可
长期自主性 100% 自己的东西，可任意魔改 受上游迭代节奏约束（但协议稳定、社区活跃十余年）

12.2 结论与建议

  • 你的三个回答已经把范围收得很清了：自用+小团队（授权要简单） + 要 E2EE —— 这两条恰好都是 B 路线的舒适区：E2EE 是 Syncthing 的默认形态，中继只转发密文，无需你额外设计加密层。
  • 建议 B 起步，但把引擎关进一层"适配层"（自己的接口 + 配置文件生成 + 进程守护），将来真要做自己的引擎，替换的是这一层，不动上层业务。
  • 唯一需要接受的结构性妥协：B 的授权是"管理型授权"而不是"密码学授权"。对这个使用范围，够；若哪天要对外销售，需要重估（届时 A 路线或上游商业授权）。

自用小团队（本项目的实际场景） 2GB 3 ~180GB ~144 元/月
同上，但改上来的都是大文件 5GB 3 ~450GB ~360 元/月
有人误把 500GB 素材放同步目录 500GB（一次性） 4 2000GB ~1600 元（单次）

⚠️ 多端复制倍数（v0.6 新增，之前漏算）：中继只看到密文，无法做跨设备去重，所以 一次改动产生的中继流量 ≈ 改动量 × 接收端数量（未被局域网直连截住的那部分）。 上表第 1 行就是按 3 个接收端算的：2GB × 3 × 30 天 ≈ 180GB。设备越多，倍数越大。

⚠️ 但上表是"跨网流量 100% 走中继"的上界（v0.8 补充参数化公式）

G2 自己定的目标是打洞成功率 ≥ 60%，所以真实中继流量应当按成功率打折：

中继出流量 ≈ 跨网改动量 × (1 − 打洞成功率) × 接收端数量
按 60% 成功率、2GB/天、3 个接收端：2 × 0.4 × 3 × 30 ≈ 72GB/月 ≈ 58 元/月
                         按 0% 成功率（全中继）：180GB/月 ≈ 144 元/月

也就是"上表是悲观上界（钱往多了算）"。所以 E4 必须同时测打洞成功率，否则成本会按最坏情况估计。

结论： 1. 局域网优先不只是体验，是毛利——办公室内跑中继的每一 GB 都是净亏。 2. 必须有控制手段，否则一次误操作就是一张账单。但要按阶段区分（v0.8 修正与 §2.4 的矛盾）： - 阶段一：全局配额（-global-rate -per-session-rate）＋ 云监控预算告警（阿里云侧设阈值）＋ 打洞优先——设备级月度硬顶做不到（上游无按设备计量，§12.4）。 - 阶段二（W2 之后）：按设备/租户的月度硬顶与超额断流。 3. 降本手段：打洞优先（失败才中继）、块级去重（仅限单次传输内的块级复用——E2EE 下中继无法跨设备去重）、月度硬配额、超大文件引导走 OSS/对象存储；控制接收端数量本身也是一种降本（倍数效应）。 4. 现有阿里云 ECS（，2核1.6G/40G）算力够跑授权+信令+小规模中继，但带宽与内存必须实测（R8）——上线前必须压测两项，且禁止用估算数字代替实测： ① ECS 公网带宽上限（决定"20GB 跨网首次同步"的真实耗时，以及是否要升配或改按流量计费）； ② strelaysrv 并发 session 数与常驻内存的关系曲线，并确认长时大文件传输下内存不单调增长（流式转发理论上与传输量无关，需实测确认无缓冲累积）。 压测结论出来之前，中继一律按"配额 + 限速"上线。

18. 验收标准（可测）

阶段一必过：第 1、2、3、4、8、10、11 条（第 1 条按 E5 实测口径）；第 12 条在阶段一改为「未持正确 relay -token 的客户端连不上私有 relay（relay 使用准入）；而未被互加 Device ID 的设备即使拿到 token 也看不到任何文件（同步成员准入）——两层分开验」。 阶段二验收：第 5、6、7、9、13 条（授权宽限、后台吊销、离线 .lic、时间回拨、中继层即时断流）。

  1. 同网段两台设备：新增/修改/删除/重命名 4 类操作，记录各自的 P50/P95 实测值（E5），并按下表判定（局域网同步期间"经 Relay 的文件负载公网流量 = 0"——注意不是"ECS 总公网流量 = 0"：客户端仍会向 stdiscosrv 宣布/查询地址，这部分 discovery 元数据流量不计入本条）（v0.8 给出阈值，否则本条没有判定力）： | 实测 P95（新增/修改） | 判定 | |---|---| | ≤ 3s | ✅ 达标 | | 3–10s | ⚠️ 可接受，但须在报告里写明原因（如 fsWatcherDelayS 默认 10s）与是否调优 | | > 10s | ❌ 不达标，必须给出缓解措施（调小 fsWatcherDelayS / 客户端事件后主动触发 scan / 明确该项为"最终一致"并写入验收标准） | 删除/重命名单列，允许更宽松，但必须记录实测值。服务端公网流量为 0。
  2. 20GB / 5 万文件首次同步：不丢文件、不产生重复文件、支持断点续传。
  3. 拔网线 5 分钟后恢复：自动补齐，无重复传输，无异常冲突副本。
  4. 跨网（家中 → 公司）：无需任何手动配置即自动建立连接（能直连则直连，否则回落 relay）。具体秒数按 E6 实测后确定的 SLA 判定——此前写的"5 秒"未经验证，已撤为待定（v0.9）。
  5. 授权到期：进入宽限期提示明确，宽限期满按配置降级，任何情况下不删用户数据。
  6. 后台吊销设备：5 分钟内该设备停止同步且提示原因。
  7. 隔离内网：导入 .lic 后可完整同步，无公网依赖。
  8. 双端并发修改同一文件：产生冲突副本，原文件不丢，两个版本均可打开。
  9. 系统时间回拨 24 小时：授权状态不被延长，进入宽限倒计时。
  10. 卸载客户端：不残留同步文件、不留后台上传进程。
  11. 版本恢复（按 Syncthing 原生语义，v0.9 重写）：在确有该版本归档的设备上，用 UI 选择版本并恢复成功；恢复后该文件按正常变更重新同步到其它设备；不承诺"任一设备恢复任意版本"，也不承诺"另存为新文件名"。
  12. 把中继凭证复制到另一台设备使用：relay 握手被拒（凭证绑定 Device ID）。
  13. 后台吊销设备后：该设备在中继层 ≤5 分钟断流（不只是本地停止同步）。

理由：正常客户端收到心跳 403 后会停同步，5 分钟目标在"客户端层"能满足。但已签发的 Token 仍然有效，用户绕过你的壳直接跑原版 Syncthing 连 relay，relay 无法拒绝——因为 relay 只做密文转发，不查授权状态。FR-4.12 写的"防破解主闸门 = 中继 Token 必须服务端签发且短时效"，24h 恰恰破坏了"短时效"这个前提。

修正建议：单 Token 时效保持 ≤1h，批量签发 24 张；或 relay 侧维护一张"已吊销 Device ID 黑名单"（授权服务推送，relay 内存查表），使吊销在 relay 层也即时生效。后者更彻底，且 strelaysrv 本身基于 Device ID 鉴权，加一张黑名单的改动量很小。

R6 与 FR-4.11 边界缺失

结论："授权服务连续 5xx 时静默重试不弹窗"缺少时间上限，持续到宽限期倒计时启动后仍静默，与 FR-4.11"绝不静默降级"冲突。

理由：5xx 不是授权状态变化，短期静默合理。但如果 5xx 持续数天，客户端已进入宽限期倒计时却没弹窗，用户对即将到来的降级一无所知——这正是 FR-4.11 要防的"静默降级"。

修正建议：R6 补一句"静默重试窗口 ≤ 心跳间隔 ×3 或宽限期剩余时长的 20%（取小者），超限即弹窗告知'授权服务不可达，已进入宽限期'"。

回答你的两个小事

1. R2 批量 Token 被提取的风险

结论：风险真实存在但可封死——Token 必须绑定 Device ID（= Syncthing 证书指纹），relay 侧握手时校验连接方 TLS 证书与 Token 绑定 ID 一致。

依据：Syncthing 的 Device ID 本身就是设备证书的 SHA-256 指纹，relay 协议握手时天然携带证书。攻击者提取了 Token，但没有对应设备的私钥，无法完成 TLS 握手，relay 直接拒绝。这不是额外开发——strelaysrv 的鉴权机制已经基于 Device ID，你的自研层只需要在签发 Token 时把 Syncthing Device ID 写进 Token claims，relay 侧加一层校验即可。

剩余风险：吊销后已签发 Token 在剩余有效期内仍可用（见上文 R2 冲突），需靠"relay 黑名单"或"缩短时效"解决。

2. 是否达到 PoC 标准

结论：差 3 条，补完可进 PoC。

  1. Syncthing 适配层接口未定义：PRD 说"把引擎关进适配层"，但没定义自研层与 Syncthing 的交互接口——配置文件怎么生成、events API 怎么监听、进程怎么守护启停。PoC 第一天就要写这层，不能到时候再设计。
  2. E2EE 密钥分发与轮换流程缺失：D3 已决要 E2EE，但新设备入网时密钥怎么分发、设备丢失后怎么轮换密钥、轮换后旧密钥加密的历史版本还能否解密——这些在 PoC 里就会碰到（双机同步就要初始化密钥）。
  3. 中继鉴权方案未二选一：§9.4 写的是"自研 Token 协议"，但 Syncthing relay 有自己的 Device ID 鉴权机制。是自研 Token 叠加在 relay 之上，还是直接复用 Syncthing Device ID 白名单（授权服务推送给 relay）？两条路实现完全不同，PoC 前必须定。 　⚠️ 订正（v0.8 附加）：本段原文中"Syncthing relay 有自己的 Device ID 鉴权机制"已被源码核验推翻（Device ID 只用于身份与路由，不用于准入，见 §12.4）；"逐设备白名单"上游不存在，属 W1 工作项。

数据存在哪里？ 只存在你自己的设备上。v1 不在云端存任何文件副本；阿里云 ECS 只跑信令、授权、中继（且只转发密文）
云端（含中继）能看到什么？ 设备 ID（证书指纹哈希）、连接时间与时长、字节数、folder ID、账号与 License 数据（阶段二）
云端看不到什么？ 文件内容、文件名、目录结构、修改时间、块哈希明文
谁能访问这些元数据？ 你（服务器 root + 后台管理员）；阿里云作为云服务商在物理与管理层可接触磁盘，但拿到的是密文与上述元数据
数据保留多久？ 端侧：所有版本历史/回收站按 §FR-3.3（默认 30 天）。云端：心跳/流量/审计日志按 §FR-5.6（≥180 天）；文件内容不留
第三方托管风险 只有阿里云一家；无第三方 SaaS、无第三方中继、无官方公共发现节点（D3/R11）
设备丢失怎么办？ 从其它设备的信任列表移除该 Device ID（＝该设备再也无法参与同步）；阶段二可额外在中继层吊销
出问题时怎么自证？ 本附录 + §12.3-8 威胁模型 + 中继只转发密文这一事实 + 可自行抓包核验
