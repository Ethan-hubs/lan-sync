5. 结论 D：把 Syncthing 注册为 Windows Service——sc create 直接包 console 程序会启动失败

尝试 结果
sc.exe create LanSyncEngine binPath= "...\syncthing.exe serve --home ... --gui-apikey ..." → Start-Service ❌ CouldNotStartService；服务保持 Stopped（SCM 要求进程以服务协议向 SCM 汇报状态，普通 console 程序满足不了）
引擎进程本身 ✅ 能跑（监听 22000、GUI 可达、跨网同步正常）

结论 + 现成答案：M1 的"引擎以 Windows Service 运行"必须配一个服务包装器。核实了上游生态的现成做法：

  • Bill-Stewart/SyncthingWindowsSetup（4,280★）——它的安装包内部就用 shawl.exe 作为服务包装器 （README 原文："shawl.exe | Helper program for running Syncthing as a Windows service"）， 并用 asmt.exe 管理服务账号（含"以服务身份登录"权限、重置账号口令）、ServMan.exe 启停服务。
  • 所以 M1 的正确做法是 引入 shawl（或 NSSM/WinSW 同类）注册引擎服务，并处理两件容易被忽略的事： ① 服务账号（非 SYSTEM 时）需要"作为服务登录"权限；② 同步目录要给该账号 Modify 权限 （上游文档给的命令格式：icacls "<dir>" /grant "SyncthingServiceAcct:(OI)(CI)M" /t）。

6. 结论 E：测量工具本身的三个坑（都踩过并修好）

# 坑 症状 修法
E1 PowerShell 5.1 的 Register-ObjectEvent 处理器不会在主线程阻塞时运行 用 Start-Sleep -Seconds 110 等窗口 → 事件全部堆到脚本结束时才写盘，记录的"到达时间"是派发时间：测出 89–103 s，真实值 ~3 s 用 $Event.TimeGenerated（事件生成时刻）记录，并把等待改为 200 ms 短睡循环；本版已同时记录 utc_ms 与 dispatch_ms 作为自证
E2 无 BOM 的 UTF-8 .ps1 被 PS 5.1 按 GBK 解析 中文字面量变乱码 → 字符串缺少终止符 整个脚本不执行（连续两次踩到） 推送脚本时加 UTF-8 BOM；关键采集脚本一律写成纯 ASCII
E3 经 cmd.exe 的 -EncodedCommand 有 8191 字符上限 4.5 KB 脚本 → base64 ≈ 12 KB → 命令行太长，什么都不执行 长脚本走 scp + -File，短命令才用 EncodedCommand（自动化脚本已按 2.7 KB 阈值分流）

9.3 ⚠️ 新发现：Syncthing 的 NAT 穿透会默认使用公共 STUN 服务器

Desktop-B 的日志明确写出：Resolved external address ... via=stun.voip.aebc.com:3478。 这与我们"不依赖任何公共服务"的既定目标（PRD §7 / R11 关闭官方 discovery 与公共 relay）存在缺口： STUN 也是第三方公共服务。私有化部署必须二选一：

  1. 自建 STUN（coturn 只开 STUN 功能，成本极低），配置指向自己的服务器；或
  2. 明确接受"仅打洞时需要 STUN"，并在文档里写明这条外部依赖（含隐私影响：STUN 服务器会看到设备公网地址）。

这条已加入 PRD 待修清单："关闭官方 discovery/relay" 要扩展为 "……并处理 STUN 依赖"。

10.3 实测：这台 ECS 的公网带宽（比端口更关键的数字）

方向 实测

含义（要写进 PRD §13 / §D5）：

  • 中继放在这台 ECS 上，跨网同步的硬上限就是 ~3.34 Mbps（≈ 25 MB/分 ≈ 1.5 GB/小时）。
  • 一次 20 GB 的跨网首次同步经中继要 ≈ 14 小时；这还只是带宽瓶颈，未计费用。
  • 按 0.8 元/GB 折算：满速跑满一小时 ≈ 1.5 GB ≈ 1.2 元/小时；若按固定带宽计费（3–5 Mbps 档）则与流量无关。
  • ⇒ PRD §D5"先用现有 ECS 验证"成立（功能可验），但"长期用它当中继"需要重新评估： 要么升配带宽，要么把策略做成"打洞优先 + 中继兜底"，要么中继只服务小文件/元数据。

10.7 ⚠️ 关键性能数字：经阿里云中继的实际吞吐 ≈ 1.2 Mbps

用同一个 20 MiB 不可压缩文件做定点测量（Z → 阿里云中继 → Desktop-B）：

指标 实测
端到端耗时 136.7 s
有效吞吐 1.23 Mbps
中继 bytesProxied 增量 21,041,253 B = 20.1 MiB（再次确认 1.00×，成本按 bytesProxied 直算）
对比：ECS 裸链路出网 3.34 Mbps（同一台机器、无中继转发、SSH 传输实测）
对比：此前 Azure 中继（不同文件构成，仅供参考） 33.8 MB / ~60 s ≈ 4.5 Mbps

结论与影响（要回填 §13/§14）：

  1. 中继放这台 ECS 上，实测吞吐只有 ~1.2 Mbps（比裸链路 3.34 Mbps 还低约 2.7 倍）—— 多跳转发（Z→ECS→家庭）、小机器（2 核 1.6G，还跑着宝塔站点）、TCP 跨长 RTT 三样叠加所致。
  2. 换算：20 GB 跨网首同步 = 37 小时（按 1.23 Mbps）；即便按裸链路 3.34 Mbps 也要 14 小时。
  3. 因此中继的定位必须是：打洞/直连失败时的兜底 + 小文件与元数据； 大文件跨网不能指望中继（要么打通直连，要么用户自己走别的通道）。
  4. 成本：1.23 Mbps 满速 ≈ 0.55 GB/小时 ≈ 0.44 元/小时；若真跑满 37 小时（20GB）≈ 16 元/次。
  5. 若要当中继长期用：升带宽（阿里云带宽单价高）或换按流量计费的更大机器； 更划算的方向是把打洞成功率做上去（这也是 PRD §G2 的观测指标）。

安全提示：切换过程中 PowerShell 回显把完整 relay URI（含 token）打印到了日志里。 该 token 只是我们自建中继的共享准入串，影响面限于"蹭中继带宽"。 建议轮换一次：改 /etc/lansync/relay-token → systemctl restart lansync-relay → 两端更新 URI（3 分钟）。
