3. 结论 B：大小写碰撞（Linux→Windows）——Syncthing 会识别并拒绝，但会卡住文件夹

在 Azure（大小写敏感）创建仅大小写不同的两个文件：

CaseTest.txt  → 内容 "lower-name"（10 字节）
CaseTest.TXT  → 内容 "upper-ext"（9 字节）

Windows（NTFS 大小写不敏感）实测结果：

现象 证据
只有一个文件落地 CaseTest.TXT（size=9，"upper-ext"）
Syncthing 明确报错，不是静默覆盖 ✅ folder/errors：remote "CaseTest.txt" uses different upper or lowercase characters than local "CaseTest.TXT"; change the casing on either side to match the other
留下残留临时文件 ~syncthing~CaseTest.txt.tmp（size=10，"lower-name" 的内容）
文件夹永远无法进入"完全同步" needFiles 持续 = 1（state=idle 但队列非空），删掉碰撞文件对后立即恢复 needFiles=0 errors=0
附带发现 该错误项会拖慢整个文件夹的同步：清理前测得的批量时延被推到 ~90 s，清理后恢复正常

产品含义（要写进 PRD 与 Adapter 契约） 1. 好消息：不会静默丢数据（此前担心的"互相覆盖"被实测否定）。 2. 但托盘 UI 必须把这类 folder error 明确呈现（红色告警 + "改一边的大小写"的处置建议），否则用户只会看到"永远在同步中"。 3. Adapter 需要提供"列出 folder 错误 + 一键清理残留 ~syncthing~*.tmp"的能力（现已确认 /rest/folder/errors 能拿到精确原因）。

4. 结论 C：>260 字符路径——能同步，但普通 API 看不见（比预想的更微妙）

用例：8 层 × 30 字符目录 + 文件名，完整路径 281 字符。

检查 结果
Windows LongPathsEnabled 注册表 0（默认关闭）
深目录（最长 267 字符）是否创建 ✅ 创建了
目标文件是否同步过来 ✅ 同步成功（Syncthing 内部使用长路径感知 API）
用 Get-ChildItem -Recurse 能否枚举到该文件 ❌ 看不到（返回 0 个文件）
用 \\?\ 前缀访问同一路径 ✅ Test-Path = True

产品含义：Adapter / 托盘 / 报表在做"扫描文件、展示列表、计算占用"时， 必须使用扩展长度路径（\\?\）或启用长路径清单，否则会出现"文件明明同步了、界面里看不见"的诡异现象。 PRD §FR-1.6 的表述要从">260 需 \\?\（引擎侧）"扩展为"引擎可同步；UI/Adapter 侧也必须用扩展路径访问"。

5. 结论 D：把 Syncthing 注册为 Windows Service——sc create 直接包 console 程序会启动失败

尝试 结果
sc.exe create LanSyncEngine binPath= "...\syncthing.exe serve --home ... --gui-apikey ..." → Start-Service ❌ CouldNotStartService；服务保持 Stopped（SCM 要求进程以服务协议向 SCM 汇报状态，普通 console 程序满足不了）
引擎进程本身 ✅ 能跑（监听 22000、GUI 可达、跨网同步正常）

结论 + 现成答案：M1 的"引擎以 Windows Service 运行"必须配一个服务包装器。核实了上游生态的现成做法：

  • Bill-Stewart/SyncthingWindowsSetup（4,280★）——它的安装包内部就用 shawl.exe 作为服务包装器 （README 原文："shawl.exe | Helper program for running Syncthing as a Windows service"）， 并用 asmt.exe 管理服务账号（含"以服务身份登录"权限、重置账号口令）、ServMan.exe 启停服务。
  • 所以 M1 的正确做法是 引入 shawl（或 NSSM/WinSW 同类）注册引擎服务，并处理两件容易被忽略的事： ① 服务账号（非 SYSTEM 时）需要"作为服务登录"权限；② 同步目录要给该账号 Modify 权限 （上游文档给的命令格式：icacls "<dir>" /grant "SyncthingServiceAcct:(OI)(CI)M" /t）。

6. 结论 E：测量工具本身的三个坑（都踩过并修好）

# 坑 症状 修法
E1 PowerShell 5.1 的 Register-ObjectEvent 处理器不会在主线程阻塞时运行 用 Start-Sleep -Seconds 110 等窗口 → 事件全部堆到脚本结束时才写盘，记录的"到达时间"是派发时间：测出 89–103 s，真实值 ~3 s 用 $Event.TimeGenerated（事件生成时刻）记录，并把等待改为 200 ms 短睡循环；本版已同时记录 utc_ms 与 dispatch_ms 作为自证
E2 无 BOM 的 UTF-8 .ps1 被 PS 5.1 按 GBK 解析 中文字面量变乱码 → 字符串缺少终止符 整个脚本不执行（连续两次踩到） 推送脚本时加 UTF-8 BOM；关键采集脚本一律写成纯 ASCII
E3 经 cmd.exe 的 -EncodedCommand 有 8191 字符上限 4.5 KB 脚本 → base64 ≈ 12 KB → 命令行太长，什么都不执行 长脚本走 scp + -File，短命令才用 EncodedCommand（自动化脚本已按 2.7 KB 阈值分流）
